> 日期：2026-10-11
> **范围声明（用户拍板）**：**只按生产代码本身该怎么分**——测试怎么组织、能不能在无引擎进程里跑、
> 哪些类型"纯"到能单测，**本方案一律不考虑**（之后再单独议）。
> 状态：**方案，未执行**。判据 = 生产行为零改动（主场景与读数场景 headless 逐字同基线）。
> 作废：前一版"领域优先"、以及"按运行时纯度分层"的论证（理由见 §五）。

## 〇 一句话

**顶层 = 层（这是什么），层内 = 领域分组（它是哪一块）。** 加文件只问一个问题：
"**这是什么？**" → 查表 → 放。不需要先在心里建领域模型，也不需要判断"它纯不纯"。

## 一 现状：三层，但每层内部换了一把刀

| 刀 | 回答 | 用在哪 |
|---|---|---|
| ① 运行在哪 | 要不要 Godot | `Assets` 的存在理由 |
| ② 是什么层 | 数据 / 逻辑 / 表现 | `Logic` vs `Scene` |
| ③ 属于哪个领域 | 世界生成 / 参数 / UI | `World.Render.*`、`World.WorldGen` |

实测出来的后果（详见附录 A）：

- `scripts/Scene/` 内部按**身份**分了子命名空间（`World.Render` / `.UI` / `.Controllers` / `.Constants`）✅ 清楚；
- `scripts/Logic/` 内部 **36 个文件全叫 `World.WorldGen`** ⇒ **这一层的命名空间不承载信息**；
- **10 个文件的命名空间与目录对不上**：6 个地图模式 ＋ 2 个叠加层 ＋ 模式注册表 ＋ 根管理器 `WorldRoot`；
  而它们的基类 `MapMode` 在 `World.Render` ⇒ 一个概念劈成两半；
- **目录重名**：`scripts/Scene/`（C# 代码）与 `scenes/`（Godot 场景文件）——每次说"Scene"都要先分辨一次；
- **孤儿命名空间**：`Temperature.cs` 声明 `World.Planet`（全仓唯一）。

⇒ "新文件放哪"没有单一答案，每加一个文件都要重新推理一次。这就是"看不懂"的机制。

## 二 目标：八层

```
scripts/
├── Data/      数据层     · 纯数据形状：世界定义 / 载体 / 词表 / 标定常量
├── Params/    配置层     · 参数存储与实例：读档 / 存档 / 改参数
├── Utils/     工具层     · 无状态工具：噪声 / 随机 / 球面几何 / H3 绑定 / PNG / 场景依赖解析
│                          ★可用 Godot 依赖（2026-10-11 用户拍板"util 也放开吧，可以放 godot 依赖的工具"）：
│                            允许 = **类型与结构**（Node / NodePath / Vector3 / Color）；
│                            禁止 = **运行期引擎调用**（`GD.*`）——无引擎宿主的单测进程里是进程级崩溃。
│                            边界由 `ArchitectureContractTests.Utils_MayUseGodotTypes_ButNoEngineRuntimeCalls` 钉住。
├── Logic/     逻辑层     · 世界的规则与计算：六阶段管线 / 投影 / 区域 / 水文
├── Render/    表现层     · 世界怎么画：网格视图 / 地图模式 / 叠加层 / 调色
├── UI/        界面层     · 面板与控件：地图坞 / 信息卡
├── Client/    客户端层   · 引擎侧外围：相机 / 输入 / 呈现设置
└── Scene/     装配层     · 场景怎么搭：根管理器 / 子系统契约 / 世界组件
scenes/                   · Godot 场景文件（.tscn）
```

### 2.1 依赖方向（只向下，且引擎侧三层互不引用）

```
                  Scene
            ┌───────┼───────┐
          Client  Render   UI        ← 引擎侧三层：平级，互不引用
            └───────┼───────┘
                  Logic
                    ↓
                  Utils
                    ↓
                  Params
                    ↓
                   Data
```

| 规则 | 内容 |
|---|---|
| R1 | 只向下依赖；**上层不得被下层引用** |
| R2 | 引擎侧三层（`Scene`/`Render`/`UI`/`Client`）**平级、互不引用**——它们之间只经 `Scene` 接线 |
| R3 | 命名空间与目录**一一对应**（见 §2.2） |
| R4 | 每层只有一个身份；一个类只能属于一层（混身份的类要拆，不是要"放中间"） |

### 2.2 "这是什么？" → 放哪（背这张表）

| 你要加的东西 | 层 | 命名空间 |
|---|---|---|
| 世界定义 / 数据形状 / 载体 / 词表 / 物理常数 | `Data/` | `World.Data` · `World.Constants` |
| 参数读取 / 参数实例 / 改参数 / 存档配置 | `Params/` | `World.Params` |
| 噪声 / 随机 / 插值 / 球面几何 / H3 绑定 / PNG | `Utils/` | `World.Utils` · `World.Utils.H3` · `World.H3Grid` |
| 生成算法 / 解算器 / 管线阶段 / 世界事实 | `Logic/` | `World.Logic` |

★命名空间去掉 `World.Render.UI` 这层嵌套：**UI 与 Render 是平级的两层**，不该一个套在另一个里面。

## 四 生产侧契约（只保留与"能不能生产"有关的两条）

1. **只向下依赖**（R1）：`Data` / `Utils` / `Params` / `Logic` 不得引用 `Render` / `UI` / `Client` / `Scene`；
   实现方式仍是既有的反射契约（`ArchitectureContractTests` 里那条"新线不依赖旧线 + 命名空间清单"的写法）。
2. **引擎侧三层平级**（R2）：`Render` / `UI` / `Client` 互不引用；跨层协作只经 `Scene` 注入。

**暂缓（本轮不做，列入"测试之后再议"）**：
磁盘白名单、引擎面唯一、纯层不得出现引擎 API、`[Export]` 结果钉、契约测试的路径断言更新、
`Vector3` 的纯度口径 —— 这些都与"怎么测/能不能测"绑定，等测试那轮一起定。

**附带的类内务**（生产侧也确实该做，但**不属分层**，单列）：
`WorldGenSimulation.cs` 里有一处 `GD.*` 打印。按"逻辑层不掺引擎与判读"的既有原则，
它应当移进诊断场景；本轮**可做可不做**（做与不做都不影响分层成立）。

## 五 为什么是这一版（三版对比）

| | 领域优先（作废） | 运行时纯度优先（作废） | **按架构分层（本版）** |
|---|---|---|---|
| 顶层 | `WorldGen/ Params/ Shared/` | `Core/ Host/ Scene/` | `Data/ Params/ Utils/ Logic/ Render/ UI/ Client/ Scene/` |
| "放哪"要问几次 | 两问（领域→层） | 一问（能否单测） | **一问（是什么）** |
| 与你既有做法 | 要新造"领域"概念 | 要新造"纯度"概念 | **沿用**你已有的 `World.Data` / `World.Utils` / `World.Render` |
| 与测试的关系 | 无关 | **完全为测试服务** | **无关**（本轮明确不考虑） |
| 加文明层 | 开新顶层 `CivSim/` | `Core/` 变杂物抽屉 | `Logic/CivSim/` + `Data/CivSim/`（层数不变） |
| 主要代价 | 命名空间拆三类 | 命名空间拆两类 + 大量纯度整改 | 命名空间**收成一类**（`World.Logic` 取代散落的 `World.WorldGen`） |

★改版的实质理由：**分层可以作为唯一的一把刀成立**，前提是不把"运行在哪"混进来当第二把刀
——而"运行在哪"恰恰只对测试重要，对生产布局不重要。
