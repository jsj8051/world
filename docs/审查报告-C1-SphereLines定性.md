## 2 核验①当前语义：「球面线带 / 区域边界」这个生产概念还在吗？

### 2.1 地图模式层：没有任何边界线元素

> **路径注记（2026-10-06 目录治理后）**：本报告取证时文中路径为
> `scripts/worldgen/WorldGenMapModes.cs`；该文件现已归位到
> `scripts/Render/Modes/WorldGenMapModes.cs`（B 步，纯 `git mv`，内容未变）。
> 下文保留取证当时的路径写法，不改写历史事实。
> 引用该文件时请按新路径查找。

`scripts/worldgen/WorldGenMapModes.cs` 四个模式全部是**逐格填色**：

| 模式 | 表达方式 |
|---|---|
| `ElevationMode` | 逐格海拔分档色 |
| `LandSeaMode` | 逐格连续场发散色带 |
| `RegionTypeMode` | 逐格七类区域固定色（**区域之间靠色块区分，不画边界线**） |
| `CoastDistanceMode` | 逐格离岸距离色带 |

⇒ ★**地质区域边界当前用"色块相邻"表达，不用"边界线"表达**。
新架构从未提出"需要区域边界线"这个需求。

### 2.2 现行系统里最接近的东西：`RiverLineOverlay`（球面线带，但是另一条技术路线）

| 维度 | `SphereLines`（待判） | `RiverLineOverlay`（现役） |
|---|---|---|
| 表达内容 | 任意球面点串的线带 + 端帽 | 河线 ribbon（chain 化 + 边去重） |
| **分层手段** | ★**两遍深度预写**（第一遍 `ALPHA=0` 但 `depth_draw_always` 写深度；第二遍 `depth_draw_never` 只画深度命中的最近层） | ★**径向抬升**（1.0030~1.0065 档位分层） |
| 抬升后果 | 零抬升 ⇒ 无掠射角位移 | ⚠️ **已被判为缺陷**：抬升在掠射角下换算成横向屏幕位移（实测 14.6px ≈ 10% 格宽） |
| miter 接头 | ✅ 有 | ❌ 未实现（`river_surface.gdshader` 搜 `miter`/`cap` 无匹配） |
| 圆盘端帽 | ✅ 有（`CapSegments=12`，按坐标去重） | ❌ 无 |

⇒★**两者不是"同一件事的两个实现"，而是两条独立技术路线**，
且现役那条（径向抬升）**正是本项目已判定的错误做法**。

### 2.3 另一个相关类：`CellQuery` 的选中环带（也不需要两遍预写）

`scripts/Render/CellQuery.cs` 的环带用 **NDC深度偏移（UV2.y）** 解决分层，
**零世界位移**—— 与决策 08/架构文档 §6 的渲染规范完全一致。

⇒★**当前渲染层已经统一到"NDC bias 代替物理抬升"这条路线**，
`SphereLines` 的两遍深度预写是**同一问题的另一种解法**，但服务的是不同的表达需求
（线带 vs 闭合环带）。

### 2.4 核验①结论

> **「球面线带 / 区域边界」作为独立生产概念，当前架构中不存在需求。**
>
> - 地质区域用色块表达，不需要边界线
> - 唯一在用的球面线带（河流）走的是另一条技术路线，且那条路线已被判为有缺陷
> - 选中环带走 NDC bias 路线，与两遍预写无关
>
> ⇒ **现行语义已消失**（不是"被替代"，是"需求本身不存在"）。

## 3 核验②现行替代：谁承担同样效果？

| 需求 | 现行承担者 | 状态 |
|---|---|---|
| 地质区域视觉区分 | `RegionTypeMode`逐格七色 |✅ 够用（色块相邻） |
| 球面线带（河流） | `RiverLineOverlay` + `river_surface.gdshader` | ⚠️ 走径向抬升路线，抬升问题已被判为缺陷（待 v2.1 修） |
| 贴地半透明环带 | `CellQuery` + NDC depth bias | ✅ 已合规范 |
| **两遍深度预写（避免重叠边重复混色）** | **无** | ❌ 无替代者 |

★**关键区分**：`SphereLines` 解决的是一个**现役系统尚未解决的问题** ——
"线带/端帽在角点处必然几何重叠，怎样让每像素只混色一次且半透明不叠加变深"。
`RiverLineOverlay` 走抬升路线恰好**没有解决**这个问题（抬升只是让干流盖住支流末端）。

⇒ 也就是说：`SphereLines` 的**技术思想仍有价值**，但**当前没有使用它的场景**。

## 4 核验③资产价值：这套实现值不值得封存？

### 4.1 它的技术思想（三层，缺一不可）

```
第1 层· 两遍深度预写
   第一遍：ALPHA=0 隐形光栅化，但 depth_draw_always【写深度】
   第二遍：depth_draw_never，只画深度命中的最近层
   ↓ 效果
   线带/端帽在角点处【必然几何重叠】→ 每像素却【恰混色一次】
   → 半透明线色【也不叠加变深】
   ↓ 约束
   遍顺序必须由 render_priority 钉住（透明队列按深度排序会乱，注释明记"实测必钉"）

第 2 层 · miter 接头
   正 m 边形下"角点的径向"恰好是【内角平分线】⇒ 标准 miter 接头
   → 六个转角不断、不豁口
   但沿平分线偏移 h 时，环带垂直于边的净宽度 = h·cos(π/m)
   ⇒ 必须【预先补 1/cos(π/m)】才能使实测宽度等于目标

第 3 层 · 圆盘端帽
   线半宽的端帽圆盘【填楔形缺口】（圆角衔接）
   全实例【按坐标去重】——共享角点只补一次帽
```

### 4.2 与本项目已冻结规范的关系（重要）

`architecture.md §6` /决策 08 的表现层渲染规范：

> **不得通过 world-space radial lift 实现图层排序**；
> 需要分层时，几何保持真实表面位置，排序通过 depth / NDC bias、stencil 或 overlay pass。

⇒ ★**`SphereLines` 的两遍深度预写正是这条规范的早期实践**（2026-09-10），
它用"深度预写 + 遍顺序"达成了"零位移分层"，
而**规范后来把这件事收敛为"NDC depth bias"**（`river_surface.gdshader` 的 `UV2.y`）。

它还记录了一个**方案固有语义（非本类缺陷）**：

> 实例之间不混色—— 深度预写按实例计，屏幕重叠时只有更近实例的线可见；
> 需要共存的线应塞进同一次 `SetLines`。

### 4.3 核验③结论

> **值得封存。** 理由不是"代码写得好"，而是：
> 1. 它解决的是一个**真实且仍未解决**的问题（重叠线带的一次混色）
> 2. 它的三层技术思想（深度预写 / miter 补偿 / 坐标去重端帽）**互相咬合**
> 3. 它是本项目**表现层规范的前身实践**，理解它才能理解规范为什么那样写
>
> ★与 `ParallelLoops` 的区别正在这里：
> `ParallelLoops` 是**预备但从未接线**（没有"它解决过什么"的历史）；
> `SphereLines` 是**完成过、有明确技术思想、被真实使用过**（后随消费者删除而orphaned）。

## 5 定性与建议

### 5.1 三条路径对照

| 路径 | 含义 | 本例 |
|---|---|---|
| 现行语义仍需要 | → 保留 / 迁移 | ❌ |
| 现行语义已消失 | → **生产删除** | ✅ 本例 |
| 现行语义已消失 + 算法有独立历史价值 | → **生产删除 + 封存** | ✅ **本例（最佳）** |

### 5.2 建议：生产删除 + 知识封存（3 个文件）

**删除**：
- `scripts/Render/SphereLines.cs` + `.uid`
- `shaders/boundary_line_color.gdshader` + `.uid`
- `shaders/boundary_line_depth.gdshader` + `.uid`

★**注意比C-3 多删2 个文件** —— shader 是自闭合单元的一部分，
留 shader 反而是"悬空资源"（比悬空类更难察觉）。

**封存**（建议写入 `docs/newdecision/封存-表现层与工具.md`）：
1. 两遍深度预写的**完整机制 + 遍顺序约束**（render_priority 必须钉）
2. miter 补偿的**推导**（`1/cos(π/m)` 从哪来）
3. 端帽的**坐标去重**约定（共享角点只补一次）
4. ★**它与现行NDC depth bias 规范的血缘关系** ——
   这是最重要的一条：规范不是凭空写的，是从这套实践收敛来的
5. **方案固有语义**（多实例不共存→ 应塞进同一次调用）
6. ★**它尚未解决的问题**：线带重叠的一次混色—— 若将来River v2.1
   或其它线带需求出现，这套思路是现成参考

### 5.3 顺带发现

`shaders/` 目录下现在只有 3 个 shader 在用：
`river_surface.gdshader`（河面 + 选中环带）、`boundary_line_color`、
`boundary_line_depth`（后两个仅服务 `SphereLines`）。
⇒ 删除后 `shaders/` 只剩 1 个文件，**"shader 目录"这一约定是否还需要独立目录**，
