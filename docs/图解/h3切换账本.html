切换 H3 的工作量账本

H3 封装好了什么（能省的） vs 我们真正消耗什么（省不了的）——交集只有我们早已实现的 10%

H3 的 API 供给现成能力

  • 细分球面六边形网格（res 0–15 分档）
  • 邻居 / kRing / 距离查询
  • latLng ↔ cell 双向索引（64 位编码）
  • 任意分辨率（只有固定 16 档）
  • 跨级精确嵌套（相邻 res 不保证顶点重合）
  • 几何/插值/河流带子/样条——它不碰几何渲染
  • 模拟语义（流向/流域/水文/CivSim）

我们真正消耗项目需求

  • 任意 n 细分（32/64/96/120/128/256 全用过）
  • 邻居 / 最近邻查询（桶索引 O(~270)）
  • 2n 精确嵌套（RenderSphere 归属映射的数学地基）
  • 存档公式 10n²+2（校验/UI/诊断全引用）
  • 流向 / 流域 / 水文 / CivSim 逻辑拓扑
  • 河流覆盖层几何（Catmull-Rom/探针/带子/防穿模）
  • 400+ 单元测试 / 诊断场景的网格假设

真切换的代价（一次性 + 永久）

  • 模拟层拓扑全重写：邻居/流向/流域/水文/CivSim 全部换索引语义
  • 存档段表格式报废：v6/v15/v3 全废，已有存档全删
  • 470+ 测试大部分重写（网格假设全变）
  • 显示 hex 格视觉毫无差别：H3 也还是六边形——对偶层白干
  • 河流渲染零收益：H3 不提供任何几何/插值能力，RiverMesh 原样重写一遍
  • RenderSphere 方案作废：细球体"2n ⊇ n 精确嵌套"在 H3 里不存在
账目结论：H3 覆盖的能力中我们只需 ~10%（细分/邻居/距离——且已稳定实现数月、有测试兜底）；我们 90% 的消耗（模拟语义、存档、河流几何、嵌套细分）H3 覆盖 0。切换 = 用 16 档固定分辨率换掉任意 n，用非嵌套换掉精确嵌套——引进三个新限制，解决零个现有问题。
唯一值得"借"的不是 H3 代码，是它的分层思想（aperture-7）：若将来渲染层要 LOD 分级，我们的 2n 嵌套天然支持四叉式分层，不需要 H3。判断标准：只有当项目转向真实地理数据 / 在线地理服务 / 跨平台网格交换时，H3 才值得评估——那是产品方向问题，与工作量无关。
