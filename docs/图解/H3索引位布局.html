H3 索引为什么是 64 位（ulong）

一个"格子地址"= 基底格 + 15 级路径方向，全部塞进一个定宽整数 —— 光路径就 45 bit，int（32 bit）装不下

64 位索引的位布局（bit 63 → 0）

reserved×5
mode 3
方向数字 15 级 × 3 bit = 45 bit
base 7
res 4
保留位 5 模式 3 层级路径 45 基底格 7 分辨率 4 合计 = 64 bit
45 位路径展开：每高一级的格子，它的索引就比父格多 3 bit 方向数字 —— 格子的地址就是它的族谱。res 0 只有 19 bit 被用上，但容器必须按最深的 res 15（45 bit 路径）定宽 —— 全体索引共用同一个 64 位空间。

为什么 int 装不下 —— 光路径就超了

字段位宽说明
分辨率 res4 bit0–15，正好 4 bit
基底格 base cell7 bit0–121，正好 7 bit
方向数字45 bit15 级 × 3 bit —— 单这一项就超过 int 的 32 bit
模式 / 保留3 + 5 bit类型标记 + 扩展余量
32 位最多表示 2³² 个状态；而"H3 格子"这个状态空间本身需要 64 位才能装下（尤其最深 15 级的路径）。这不是"格子太多"的问题，是地址编码就要这么多位。

ulong 的三个直接理由（对内对外都是硬约束）

理由细节
C API 契约就是 uint64_th3api.h 所有 cell/vertex 参数全是 uint64_t。P/Invoke 侧必须 ulong 无损对齐 —— 用 int 会丢高位，索引直接变非法
无符号、按位运算索引没有负数语义；层级操作是纯位运算（找 parent = 右移 3×层级差截位），用有符号整型反而要防符号扩展
标准字符串 = 16 位十六进制H3ToString 输出 8928308280fffff（15 位以内前导 0 省略）—— 就是完整 uint64 的 hex 表示，存档/交换都按 64 位走
一句话：H3 的设计是"把整个层级路径编码进一个定宽整数"，64 位是这个设计的最小容器；ulong 就是 C 端 uint64_t 在 C# 里的唯一无损对应。换成 int 不是省内存，是直接破坏索引语义。
附赠一个相关事实：顶点 id 同样是 64 位（mode=3）—— 所以门面里 CellToVertexes 返回 ulong[]。你的两遍构建里 HashSet<ulong> 存的正是这种顶点 id，别想着"转换后再压缩成 int 本地索引"——共享顶点去重必须发生在 64 位空间，等收集完了再映射成紧凑 int 数组做渲染（那正是第三遍索引缓冲做的事）。
