坞面板升降的几何：offset_top 到底在说什么

锚点 = CenterBottom（top=bottom=1.0）→ 屏幕坐标：rect.top = 屏高 + offset_top

收起态（只露标题条）offset_top = -30

rect.top = H + (-30) = 屏高-30 → 面板**最上面 30px**（标题条）正好留在屏幕内，
其余 h-30 像素滑出屏幕底缘之外 → 视觉上"坞收起来了"。

展开态（全露）offset_top = -h（h=面板高）

rect.top = H + (-h) = H - h → 顶边恰好抬到"屏高减一个面板高"，
整个 h 高的面板全部留在屏幕内、底边贴屏底 → 视觉上"坞升起来了"。
// 收起时 offset_bottom 同步为 +(h-30)（正号埋入屏下）→ top/bot 同增同减 → 面板高不变，纯位移 float top = expand ? -h : -CukHeadH(-30); float bot = expand ? 0f : (h - CukHeadH);

动画进行中反悔：kill 旧 tween → 从中间值折返（不跳变）

蓝线：展开动画中鼠标移出 → 红线：tween 从折返点（当前中间值）滑回 -30。
虚线是错误做法对照——若新动画从"目标值"而非"当前值"起步，面板会瞬时跳到 -30 再滑，视觉上"闪一下"。
`_expanded = expand` 在 tween 启动时就赋值（:194）→ 动画中状态机方向判定始终正确。

为什么用 60Hz 物理节拍，而不是"直接按渲染帧满帧跑"

先澄清：物理帧不是"把动画插值成 60fps"——物理帧是逻辑节拍器（固定 60Hz、真实时间），渲染帧是显示节拍器（可变帧率，性能说了算）。动画必须绑逻辑节拍，不绑显示节拍。

① 起步陡峭度：Cubic vs Quad（30fps 下首帧步幅）

② 节拍细粒度：Idle（渲染 tick）vs Physics（固定 60Hz）

一句话：渲染帧率不可控，动画不能押在它身上。固定 60Hz 逻辑节拍 + 渲染时插值取位，才能做到 "低帧率机器上也平滑、掉帧也不弹跳、时长恒定 0.25s"。

"整体高度"在哪里：面板高 = offset_bottom − offset_top（差值即高度）

两个 offset 各定一边：top 定顶边、bottom 定底边。高度 = 两差（屏高在相减中抵消，与屏高无关）。展开/收起只是同步平移 → 高度恒为 h。

展开：top=-h / bottom=0 → 露高 = h

高 = 0 − (−h) = h。底边贴屏底、顶边在屏高−h → 整个 h 都在屏内。

收起：top=-30 / bottom=+(h-30) → 露 30px，高仍是 h

高 = (h−30) − (−30) = h。两 offset 同步平移 → 高度不变，整体埋入屏下。
展开露多高 = h = Size.Y（布局真实高度：标题条+分类行+图层行+间距，内容多高露多高，代码不猜）。 所以代码不需要"高度"变量——两个 offset 的差就是高度，height 是派生的，不是存储的。

匀速（Linear）vs 当前（Quad Out）：固定时间、固定距离，但速度一个恒定一个先快后慢

位移-时间（都是 0.25s 走完 h，总距离相同）

速度-时间（同样总时间，步幅分布完全不同）

改动 = 一行（CukHud.cs:188）：SetTrans(Quad)+SetEase(Out) → SetTrans(Linear)。
均匀性：Linear 更好（30fps 每帧 13.3% 恒定）；观感：Quad 更"落定"（减速收尾），Linear 有机械感。

Size.Y 是"高度"不是"y 坐标"：尺寸 vs 位置

`Control.Size` 回答"这框多高"；"这框在哪"由 Position / anchors+offsets 管。别被名字里的 Y 骗了。
代码证据：h 在 top = -h 里是位移距离——只有"长度"才能当位移量。
本坞的 y 位置 = rect.top = 屏高 + offset_top，与 Size.Y 无关。

用户拍板方向：显式五元状态模型（当前坐标 / 收起坐标 / 展开坐标 / 滑出·滑入方向）

现状：中途折返靠"kill 旧 tween → 引擎从属性当前值续滑"——机制正确但隐式，代码看不见当前位置。
目标：五个状态量随时可推导 → 任何时刻 "从哪(start) → 到哪(target)" 都是唯一确定的。
关键改进：什么都不再猜——当前坐标实时读 OffsetTop/Bottom，目标是两个已知常量； 中途任何变化 = 杀动画 + 用 current 重算 from → to，方向由目标判定。
补正也简化：current ≠ 目标 → 对齐，不再靠 <1px 差值猜。
