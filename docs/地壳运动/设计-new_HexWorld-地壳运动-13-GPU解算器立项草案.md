### §0.1 ★两处口径更正（2026-09-27 @123 独立复核；**都改动结论**）

**更正 1（CPU 行乐观 ≈9×）**：CPU 的 **11.7 GB/s 是流式屋顶**，而本负载实测 **91.4 GB ÷ 69.3 s ≈ 1.32 GB/s**（利用率仅 11%）⇒ **带宽未饱和时"流量 ÷ 带宽 = 时间"不成立**；默认档 res5 不是 383 s/步而是 **≈3,400 s/步（≈140 h/150 步）**。
⇒ 表中"折算"列一律改称**理论界**；**只有当 S0 ② 判定 GPU 热核确实带宽受限时，流量才是主线**；否则杠杆是占用率 / ILP / 每槽指令。

**更正 2（×49 只乘了格数，漏了「迭代数的分辨率增长」）**：`cg 15.8(res2) → 22(res3)`（★这是**跨窗值**：res2 取 40 步均值、res3 取单步 ⇒ **必须同窗重测**才可当缩放律）。按 **1.39×/级** 延续 ⇒ res5 cg ≈ **42.7** ⇒ **流量 2.81 TB/步**：

| 情形（res5） | 每步 | 150 步 |
|---|---|---|
| 2.81 TB @ 384 GB/s（**100% 规格**） | 7.3 s | **18.3 min ✗** |
| 2.81 TB @ 192 GB/s（50%） | 14.6 s | 36.6 min ✗ |
| **1.40 TB（再砍 2×）@ 384 GB/s（100%）** | **3.7 s** | **9.2 min ✓（贴线）** |

⇒ **若迭代增长延续，res5 ≤10 min 需要「近乎 100% 规格带宽」与「流量再砍 2×」同时成立 ⇒ 本机很可能不可达。**
（正向副产品：**Jacobi 2.08×/级 vs MG 聚合 1.39×/级** ⇒ 差距随分辨率扩大 ⇒ 两点外推 res5 净账 ≈3.9× 量级「仅示意」⇒ **MG 在 res5 是使能项，不是优化项**。）
★**该 3.9× 是乐观界（@123 复核，2026-09-27）**：它用的是 **res3 实测单价 8.324×**，而该值在 res5 上**只会更差**——`[MGCOSTBENCH]` 层单价 **87/85/67/46 ns/槽（L0/L1/L2/L3 @res3）**，规律是**层越大越慢**；res5 的层结构 `[res5,res4,res3,res2]` 相比 res3 的 `[res3,res2,res1,res0]` **整体上移一个尺寸类**（res5 的"L3" = res2 = 5882 格，不再是 122 格）⇒ **加权单价 > 8.324 ⇒ 真实净账更小**。
**⇒ 已加派：res4 单步同时报逐层 ns/槽，把"单价随分辨率"从推断变实测。**

★**再加一层乐观（@123 代码级证据 + 架构师查出，2026-09-27）**：res3 实测单价 **8.324× 不含** MG 档每次 V-cycle 重算的**层 0 对角**——证据：`MgTraversalByLevel` 的全部自增点只在 MGVCycle 内核（`:1116/:1134/:1221/:1626`），而重算循环（`:1252-1257`）**没有任何计数器**。
⇒ **res3 单步净账的真实值 = 1.49-1.52×**（两口径；**不计该开销才是 1.572**，全价计入是上界 **1.425**）。
⇒ **3.9× 是「双重乐观」**（单价少算 + 层结构上移一档）⇒ 方向对 res5 可达性**更不利**。

★**2.08× 的来历（@123 复算纠正）**：`360(res3 均值) ÷ 173(res2 均值) = 2.08`；架构师先前写的 **2.43 = 360 ÷ 148**，而 148 是 **res2 几何档的 cg 峰值** ⇒ **均值÷峰值 = 跨统计量**。**两个增长率（2.08 / 1.39）都还是跨窗或跨统计量值，必须由 res4 同口径重测**——同一张表里禁止两套统计量。

**⇒ 决定性的一次便宜测量（比建 GPU 路径便宜两个数量级，架构师已批 09-27）**：**res4 单步 / MG 聚合档 / 只读 cg 与流量 ≈2.5-7 min**，把"迭代数是否继续涨"从假设变实测；**同窗口径**：与 res3 的读数单步比单步（或窗比窗），不许跨窗。

**⇒ 解算器侧条件（★不是 `⟺`，且与整步目标必须合取）**：**若** S0 ② 判定 GPU 热核**带宽受限**，**则**设计约束 = 流量 **≤0.72 TB/步** 且有效带宽 **≥192 GB/s（=50% 规格）**（对应 1.45 TB 口径）；**若迭代增长成立（流量升到 2.81 TB），约束变为 ≤1.40 TB/步 + ≥384 GB/s（=100% 规格）**。
⚠️ **满足上述条件 ≠ 满足「150 步 ≤10 min」**——整步还含地板（15.7-43.8 s/步）。**这是本文件最容易被引错的一处。**

**三条必须同时成立的腿**（缺一条即到不了）：
1. **解算器搬 GPU**（CPU 通道 11.7 GB/s 是硬墙：MG + 砍 2× 后仍 62 s/步 = 目标 15×）；
2. **流量砍 ≥2×**（不砍则需 94% 规格带宽，现实不可达；**若迭代增长成立 ⇒ 需 100% 规格 + 砍 2× 才能贴线**）⇒ 本立项**把"少搬字节"作为设计约束，不是后续优化**；
3. **地板（解算器之外）必须一起砍/搬**：res5 线性外推 15.7 s/步（口径 A）或 43.8 s/步（口径 B，成本分解表）⇒ **两种口径下都单独超预算 3.9-11×** ⇒ 解算器归零也到不了 10 min。

**非目标（明确不做）**：降分辨率（res2 出厂档已撤：降分辨率不是提速）｜降频复用驱动场（已双否决）｜原子加/乱序归约换吞吐。

## §2 ★架构分叉：集成路径（**架构师推荐 + 待用户确认**）

| 路径 | 优点 | 代价 | 发布可行性 |
|---|---|---|---|
| **A. Godot RenderingDevice（Vulkan compute）** | 无额外部署依赖（无 CUDA/DX 运行时）；跨厂商（NVIDIA/AMD/Intel）；与引擎 buffer/生命周期一致；可进正式构建 | 调试剖面能力弱（无 Nsight 级工具）；着色器入口与每步 readback 路径需实测 | **✓ 可发布给玩家** |

**★已拍板（2026-09-27 用户「接 A」）**：
1. **产品路径 = A（Godot RenderingDevice / Vulkan compute）**，接口按 A 冻结；**B 只允许作 S0 的一次性测量工具**（若 Godot RD 的工具面不足以量出带宽/热核屋顶），**不得成为交付形态**。

2. 由此冻结的约束（S0 必须实测确认，任一不成立即回报）：

   - **着色器入口**：具体 API 面（SPIR-V / GLSL 源、RD 的 buffer 读写与 barrier）由实施方核并写进 13-1，**架构师不预设 API 名**。

## §3 数据布局与接口（架构层契约）

1. **SoA**：所有逐格/逐槽数组拆成独立连续数组（x/y 分量分离、K/dist/邻接分离），消除 Vector3 AoS 的填充与 gather；
2. **固定 stride 邻接**：H3 每格邻居数 ≤6 ⇒ **padding 到固定 stride**（空槽权重 0）⇒ 内核无分支、无 gather、可合并访存；**空槽必须显式参与归约**（值 0）以保证确定性；
3. **按板块重排格序**（架构师建议，来自"板块作存储单元"的结论）：板内格在内存连续 ⇒ 板内遍历变流式；**只作存储顺序**，不作任务划分（板块尺寸极不均匀）；
4. **buffer 生命周期**：常驻 buffer 在档初始化时一次分配（禁每步分配）；每步**只读回**判读/诊断所需场（一次 readback），中间迭代全部驻留显存；
5. **接口**：CPU 侧只见"输入场 → 输出场"（与现有 `H3ThinSheet` 同形），GPU 后端对上层透明 ⇒ 现有调用点不改签名。

## §4 确定性红线（沿用并加强）

1. **固定分块归约**：每个输出槽的累加顺序固定（禁原子加、禁 warp 内乱序归约、禁跨块浮点重排）；
2. **固定 workgroup 尺寸与调度**：kernel 的 dispatch 尺寸 = 数据的确定函数，禁动态负载均衡；
3. **★改可测形式（路径 A 钉不住"禁 FMA 收缩"）**：GLSL 无 `precise`，SPIR-V 的 NoContraction 由 Godot 编译链决定 ⇒ 红线表述 = 「**同二进制 + 同驱动 + 同 GPU，跨运行逐位同**」，并登记「**换驱动/换 GPU 即重验**」；
   ★**固有约束（见 §8，不是实现错）**：发布侧玩家驱动各异 ⇒ **逐位同在发布侧不可能成立**，对玩家的保证只能是"物理量落带 + 世界线事件一致"；
4. **补**：`RebuildCoarseKFromFine` 是 **segmented scatter-add** ⇒ 同样必须"无原子 + 固定分块"，否则整条确定性链断（MG 聚合档必经，别漏）；
5. **等价口径**：GPU 档 vs CPU 档**不要求逐位同**（与预条件子切换同理，已与 12 号口径一致），要求 ①**同 GPU 档（同二进制+同驱动）跨运行逐位同** ②物理量落带 ③同窗事件计数对照；
6. **默认档不动**：GPU 档走显式开关，默认 false，直到单独拍板切换。

## §5 精度与流量预算

- **计算精度**：fp32（保持本构/屈服的数值行为）；
- **可选存储精度**：fp16/bf16 存储 + fp32 累加 ⇒ 流量 ÷2 —— **判据用"标定式"，不发明新阈值**：以**已接受档的实测扰动当尺子**（MG vs Jacobi：maxV 0.2% / yielded 0.03%），fp16 存储引入的扰动须落在同量级带内；
- **流量预算表**（res5 口径）：目标 ≤0.72 TB/步；当前 MG 聚合档 1.45 TB ⇒ **需在 S1/S3 内再砍一半以上**。

## §7 测量项（**不设达标线**，由用户对照判读）

## §8 风险与未结项

1. **效率是否够**：规格 384 GB/s 只是纸面；若真实可达 <50% ⇒ 流量必须砍更多（或目标口径需重议）；
2. **地板**：口径 A/B 差 2.8× 未核实；若为口径 B，则地板单项就 11× 超预算；
3. **Godot RD 能力面**：读回延迟、buffer 持久化、着色器编译选项钉定 —— S0 必须实测；
4. **`pic=0 cg 3→19`** 机制未结项（12 号登记，不许写成"已解释"）；
5. 8 GB VRAM 在 res5 的驻留余量：**按代码真身粗算 ≈1.1-1.2 GB**（@123 13 审计；架构师原估 0.6-0.9 GB 偏低 1.5-2×）⇒ 仍宽松，但须把 Godot 自身/桌面占用一起量；
6. **★发布侧逐位同不可能（固有约束，不是缺陷，也不是豁免）**：玩家驱动/GPU 各异 ⇒ 只能保证"物理量落带 + 世界线事件一致"；**不许写成缺陷，也不许拿它当豁免**；
7. **★headless 下 RD 能否建 compute 设备**（S0 第一项，最可能的拦路虎，成本近零）：L0-L3 全部跑 `--headless` ⇒ 建不了则 GPU 档**进不了现有验收协议**；
8. **地板缩放类未知**：挠曲若含迭代/FFT ⇒ 非 O(N)；通量子步数**状态相关** ⇒ 可能超线性；**口径 A/B 的 2.8× 差必须同仪器、同一次运行闭合**。
