# 需求分析 · 地图浏览加载提速与加载进度反馈

- 状态：**第 1 步已通过；2026-11-11 A 修订待确认**（删校验缓存，改并行解压/解码）
- 日期：2026-11-10
- 需求：让「浏览所选地图」与「地理演化」两个加载入口变快，并在等待期间显示真实加载进度
- 流程：按需求完成指南六步闸门推进

## 一、背景

主界面有两条会加载完整世界的路径：

1. 「地图库 → 浏览所选地图」：读取 `.wmap` 包并装配只读世界；
2. 「地理演化 → 生成」：按配置生成 res4 世界，再装配画面。

两条路径点击后都会出现数秒无响应：窗口不重绘、状态文字停在“正在校验并加载地图…”或“正在生成地图…”，用户无法判断程序是在工作还是已经卡死。项目文档已把这一点记为已知限制：

- 导入是主线程同步执行，res4 约 5.5 秒，加载提示不一定来得及重绘：`docs/验证-地图导入导出.md:102`。
- 首次生成使用原有同步初始化，可能短暂阻塞界面：`docs/验收-地图生成配置.md:91`。

本轮先回答“为什么慢”，再把“变快”和“有进度”写成可验收的需求；具体技术路线留到第 2 步。

### 1.1 实测证据

测量环境：Windows、.NET 8、Godot 4.7.1 Mono、RTX 5060 Laptop；样例为本机现存的 res4 地图包 `map_20261110_000733_936.wmap`（288,122 格，216,662,566 字节，173 个数据块，解压后约 247 MiB）。

| 测量项 | 方法 | 结果 |
|---|---|---|
| 文件头探测 | `MapPackageProbe.Probe` | 73 ms |
| 读取 + 校验 + 解码 | `MapPackageReader.Read` | 4,221 ms |
| 世界事实装配 | `ImportedWorldFactsFactory.Build` | 1,974 ms |
| 导入合计（读 + 装配） | 无头 `MapImportCheck` 场景，首次运行 | 8,747 ms（墙钟 9.3 s） |
| 进程分配量 / Gen2 GC / 峰值工作集 | 分项测量所在进程 | 5,867 MB / 10 次 / 1,006 MB |
| res4 生成（t=0） | `--world 4` 内部计时 | 6,129 ms（气候 2,264 ms） |
| res4 初始生成 + 1 步演化 | `--evolve-world 4 1` | 12,881 ms |
| 其中演化步后的世界装配 | 同上 | 3,636 ms |

分项测量（4,221 + 1,974 = 6,195 ms）来自随后一次独立进程运行：系统文件缓存已热、JIT 已预热；首次无头运行是 8,747 ms。两者不矛盾，用户实际等待区间按 **6.2–8.7 秒**记。

结论：打开一张 res4 地图，仅"读包 + 装配事实"就要 6–9 秒；进入地理演化页生成世界约 6.1 秒；两者都还没有把渲染装配计入。渲染装配（122 块 × 2 档网格、28.8 万格颜色纹理、河线）未单独计时，按代码规模估计在秒级，第 2 步补测。

## 二、目的

不是“加一个转圈动画”，而是改变等待的性质：

1. **可解释**：每次加载与每步演化计算在 100 ms 内出现进度反馈，说明当前阶段、已完成量、总量与百分比（或不确定态），且数值来自真实工作量。
2. **不卡死**：浏览、生成、演化计算期间进度持续更新，主线程不出现长冻结；总时长相对现状不劣化，并在保留完整校验的前提下减少重复工作，使等待时间有可测量的下降（不设硬门槛）。
3. **可解耦**：页面加载进度由常驻层承担，演化进度由独立面板场景承担；页面只上报进度；新增加载入口不需要复制一套进度逻辑。

## 三、使用者与场景

- **玩家**：从地图库反复打开不同地图；从地理演化页生成新世界；播放、单步或跳转到目标年代（一步约 10 秒）。等待期间会怀疑卡死、重复点击或直接退出。
- **开发者**：频繁打开 216 MB 级地图做地图模式、点选、导出验证；每次数秒冻结直接打断调试节奏。
- **频率**：每次进入地图、每次生成都会发生；不是一次性冷启动问题。
- **基线环境**：本机（上述配置）与样例地图；其他机器以相对降幅验收，绝对秒数仅作参考。

## 四、现状与差距

### 4.1 慢在代码路径上

1. **浏览入口整段同步跑在 UI 线程**：`MapLibrary.TryOpen` 在同一调用栈里完成读包、装配、切换页面：`scripts/Scene/Navigation/MapLibrary.cs:115-133`。状态文字刚写入就进入 8 秒计算，期间不会重绘。
2. **每次打开都完整重读、重校验、重解码**：`ReadArchive` 遍历全部条目、逐块 `ReadEntry`，并对每个块做 SHA-256 校验：`scripts/Data/Maps/MapPackageReader.cs:45-101`（校验在 `:95`）。没有按内容哈希或文件指纹复用已解码结果的机制。
3. **同一批数据被反复复制**：`ReadEntry` 先写 `MemoryStream` 再 `ToArray`（`scripts/Data/Maps/MapPackageFormat.cs:49-68`），`Decode` 再复制成类型化数组（`:77-87`），装配层又用 `.ToArray()` 复制一遍（`scripts/Logic/Composition/ImportedWorldFactsFactory.cs:22-39`，如 `:26`、`:56`、`:70`）。5.9 GB 分配与 10 次 Gen2 GC 由此而来。
4. **渲染装配也在同一次 `_Ready` 里完成**：`MapBrowser._Ready` 依次建地图模式、初始化渲染、取景、初始化界面：`scripts/Scene/Navigation/MapBrowser.cs:49-78`；渲染初始化会建 122 块 × 2 档网格并烘 28.8 万格颜色纹理：`scripts/Scene/RenderManager.cs:73-93`、`scripts/Render/WorldView.cs:54-81`、`scripts/Render/BallView.cs:76-93`、`:177-195`。
5. **演化页生成同样同步**：`WorldRoot._Ready` 直接进入 `InitializeWorld`，`World.Initialize` 内跑 `Regenerate`（生成 + 可选初始演化步）：`scripts/Scene/WorldRoot.cs:80-135`、`scripts/Scene/WorldManager.cs:61-70`、`:114-135`。页面在 `AppRoot.MountPage` 的 `AddChild` 里入树，`_Ready` 立即执行，没有任何先渲染的机会：`scripts/Scene/Navigation/AppRoot.cs:122-131`。
6. **演化步计算已经后台化，但没有进度**：`WorldEvolutionSession.Start` 把 `CalculateToStep` 与 `PrepareEvolution` 放进 `Task.Run`，主线程只提交结果：`scripts/Scene/Evolution/WorldEvolutionSession.cs:125-141`。界面只显示“正在计算…”，等待 10 秒级的一步时同样无法判断进度：`scripts/UI/Evolution/GeologyPanel.cs:33-45`。

### 4.2 与既定设计的差距

项目设计文档已经写明加载层必须先有机会显示，再做耗时工作：“先让加载层有机会显示，再启动耗时工作，避免在子节点 `_Ready` 抢跑”：`docs/设计-地图快照与场景初始化.md:259`。当前实现与该条相反。

同一份设计还定义了带 `Progress:float?[0,1]` 与 `StageText` 的操作上下文 `OperationContext`（`docs/设计-地图快照与场景初始化.md:251`、`scripts/Scene/Navigation/SceneContracts.cs:52-77`），但生产流程没有使用它，文档自己标注“当前同步流程尚未实际使用”：`docs/验证-地图导入导出.md:106`。

### 4.3 差距清单

| 要求 | 现状 | 差距 |
|---|---|---|
| 等待期间有真实进度 | 只有一句状态文字，且来不及重绘 | 没有进度数据源；没有进度 UI 归属 |
| 先显示、再加载 | 重活发生在按钮回调和 `_Ready` 内 | 需要把“显示一帧”与“开始加载”分开 |
| 浏览要快/不卡 | 6–9 s 数据 + 秒级渲染装配，全程无帧 | 减少重复复制与串行等待；全程让出帧 |
| 进度与页面解耦 | 每个页面自行处理状态，没有共享机制 | 需要页面之外的进度承载与统一契约 |
| 失败/取消可解释 | 异常时回到原页面并显示文字 | 缺少进度态下的失败与取消收尾 |

## 五、范围

### 5.1 本次做

- 「地图库 → 浏览所选地图」：从点击到可交互的整条链路（读包、校验、解码、事实装配、渲染装配、首帧）的耗时优化与进度反馈。
- 「地理演化 → 生成」：生成、可选初始演化步、事实装配、渲染装配、首帧的进度反馈；生成耗时不劣化。
- 演化播放/单步/跳转的计算进度：覆盖构造步进与世界重建两段；跳转按目标步数汇报，单步与世界重建阶段以阶段文字 + 不确定态呈现（步级粒度）。
- 一个可复用的加载进度方案：页面加载用 `AppRoot` 常驻层，演化用独立 `EvolutionPanel` 场景；三处共用同一契约与进度视图组件；页面只上报进度，不实现进度逻辑。
- 失败与退出清理：进度态下的错误提示、返回原页面、退出时取消并释放。
- 可验证的测量与回归入口（沿用现有测试与 `tests/verify-map.ps1`）。

### 5.2 本次不做

- 不改生成算法、物理、气候、水文、演化的数值与结果。
- 不降低 res4 生产分辨率，不改世界尺度与地图模式语义。

- 不做地图库列表的虚拟化、缩略图、批量预加载。
- 不做校验缓存（A 决定）；不缓存解码结果、世界事实或显示网格。
- 不重写应用导航与生命周期，只为加载建立最小可复用契约。

## 六、约束

- 平台：Windows、.NET 8、Godot 4.7.1 Mono；Node/Resource 的创建与释放只能在主线程（`docs/设计-地图快照与场景初始化.md:263`）。
- 兼容：现有 `.wmap`、地图库列表、只读浏览、演化播放/跳转/导出流程保持可用。
- 内存：当前峰值工作集约 1.0 GB；优化不得显著恶化（具体上限待确认）。
- 取消：演化计算离开页面必须取消；页面加载不可由用户取消，退出应用时必须取消并释放；迟到的结果不得提交。
- 依赖：不新增第三方库；不改变既有 `user://` 路径语义，不新增可写目录。
- 进度真实性：百分比必须由实际完成量推导；不能是定时器动画；无法细分时显示不确定态而不是假百分比。

## 七、验收口径

以下每条都可观察、可复现。带“待确认”的数字是本轮提议值，需用户拍板后冻结。

**A. 进度可见性（浏览、生成、演化计算三个入口都适用）**

- A1 点击/开始计算后 ≤100 ms 出现进度层；进度层含进度条、百分比（或不确定态）、当前阶段文字、已完成/总量。
- A2 进度条填充比例与百分比一致（误差 ≤2%）；百分比单调不回退；完成时正好 100%。
- A3 等待期间进度至少每秒更新 10 次；阶段切换时文字与真实阶段一致。
- A4 主线程单帧阻塞 ≤200 ms（用帧时间日志验证；不允许整段数秒无帧）。

**B. 浏览加载（res4、216 MB 样例、本机）**

- B1 从点击「浏览所选地图」到可交互（可转相机、可点选、可切模式）总时长不高于现状基线（系统缓存已热 6.2 s、首次 8.7 s，另加渲染装配），劣化 ≤10%。加载期间直接构建 res4，冻结输入；100% 后才开放。
- B2 加载全程无单帧 >200 ms 的冻结，进度持续更新（与 A4 同一条验证）。

**C. 地理演化页与演化计算**

- C1 点击「生成」后 ≤100 ms 出现进度；生成、装配、首帧各阶段都有对应文字。
- C2 生成 + 装配总时长不高于现状（当前生成 6.1 s，另加渲染装配），劣化不超过 10%。
- C3 若启用初始演化步，按步汇报进度（当前 UI 不暴露该参数，作为可选路径验收）。
- C4 播放/单步/跳转期间显示后台计算进度：跳转多步时显示已完成步/总步数与百分比；单步及世界重建阶段显示阶段文字、已用时间与不确定态（不伪造百分比）。
- C5 跳转多步时进度按步单调推进；计算完成前不发布中间态（沿用现有"只提交最终候选帧"语义）。
- C6 计算期间界面保持可响应：可返回原页面；离开页面后计算停止，迟到结果不提交。
- C7 计算期间上一已发布帧保持完整可用：相机、点选、信息卡、地图模式切换都不受影响；仅播放/单步/跳转/倍率因计算中禁用。
- C8 计算完成后的切换：先禁用交互，再发布新帧并分帧重烘（纹理/河线），完成后恢复；切换期间单帧 ≤200 ms。

**D. 失败与取消**

- D1 损坏包、缺块、校验失败、版本不支持：进度层转为错误态，显示错误码与位置，停留原页面，不创建半成品世界。
- D2 页面加载（浏览/生成）为 Modal 且不提供用户取消：关闭窗口/退出应用时取消并释放；演化计算期间离开页面即取消，迟到结果不提交。
- D3 取消不作为 IO 失败展示（沿用现有错误分类约定）。

**E. 场景解耦**

- E1 页面加载（浏览/生成）的进度 UI 位于 `AppRoot` 常驻层，不以页面脚本内嵌方式创建；演化进度位于独立 `EvolutionPanel.tscn` 场景，自带进度条，页面只实例化并注入进度源。
- E2 三处进度共用同一 `LoadOperation` 契约与同一个进度视图组件（`LoadProgressView`）；新增加载入口只需上报进度并选择宿主视图，不改数据与显示逻辑。
- E3 页面节点是否存在不影响加载任务的取消语义：页面卸载或退出应用后任务可取消，结果被丢弃。

**F. 进度真实性**

- F1 抽样核对：进度 50% 时实际已完成约一半工作量（按所选计量单位：字节/块/阶段/格）。
- F2 阶段内无法细分的部分显示“不确定态”（如滚动条/“处理中”），不得用匀速动画冒充百分比。

**G. 回归**

- G1 `dotnet run --project tests/World.Tests.Local` 全绿（当前 147 项）。
- G2 `tests/verify-map.ps1` 通过（含 res4 无头导入）。
- G3 手工流程 A–D（导出、浏览、损坏拒绝、版本不支持）通过：`docs/验证-地图导入导出.md:45-75`。
- G4 演化播放、单步、跳转、导出仍可用。

**H. 资源**

- H1 峰值工作集 ≤ 现状 1.25 倍（待确认具体数值）。
- H2 不产生持续的临时文件堆积，不新增可写目录。

## 八、假设

- 上述实测来自目标开发机；其他机器以"不劣化 + 无长冻结 + 进度实时"验收。
- 216 MB / res4 是当前主要的大地图形态；接近 512 MB 上限的包不在本轮性能目标内。
- 用户所说的"浏览慢"指点击到可交互的等待，不是地图库列表枚举或地图模式切换。
- 现有 147 项测试与 `verify-map.ps1` 可作为回归基线。

## 九、已确认决策（2026-11-10）

用户以「1C 2C 3C」确认：

1. **Q1 = A**：进度覆盖进入地理演化页的初始化，以及演化播放/单步/跳转；演化计算按步级汇报，单步内部与世界重建显示不确定态（不做子步级百分比）。
2. **Q2 = C**：不设绝对秒数；只要求进度实时、不出现长冻结、相对现状不劣化。提速作为测量结果报告，不作硬门槛。
3. **Q3 修订（A）**：不做校验缓存；此前 3C（允许缓存校验结论）与 4A（中央目录指纹）作废。
5. **1B（显示位置）**：演化进度嵌入独立 `EvolutionPanel.tscn` 场景，页面加载进度留在 AppRoot 常驻层；E1 已按此修订。
6. **3B（修订）**：不做预览球；浏览直接构建 res4，加载期间冻结输入，完成后开放；演化计算期间保留上一帧完整可用（含模式切换），完成后再冻结并切换。
7. **1B / 2A / 3A**：页面加载不提供用户取消（仅退出应用时取消）；演化面板不提供“取消当前计算”按钮，离开页面即取消。

## 十、风险

1. **并行解压/解码的竞态**：多 ZipArchive、多线程解码若共享缓冲或顺序错乱，可能产生错误数据；必须每线程独立流、结果按块归位，并有逐字节对照测试。
2. **提速有限**：不缓存校验与解码结果，重复打开仍需解压 247 MiB、重建事实与网格；不设绝对秒数，只保证不劣化；并行解压与减复制是主要手段，实测值在第 6 步报告。
3. **后台化边界**：Godot 的 Node/Resource 必须主线程创建；错误地把装配放进后台会崩溃或产生竞态。
4. **单步内无百分比**：单步约 10 秒只能显示阶段文字、已用时间与不确定态；用户仍可能觉得慢。这是 Q1=A 的已知代价，验收允许不确定态，但禁止用匀速动画冒充百分比。
5. **内存上升**：并行解码、渲染装配同时存在会抬高峰值；当前已 1 GB。
6. **解耦流于形式**：进度 UI 虽外置，但重活仍压在页面 `_Ready`，症状不会消失；A1/A4 与 E1/E3 共同约束；演化面板独立成场景后，还要防止它反向依赖页面节点。
7. **取消与释放**：`ZipArchive`、大数组、已建网格、后台演化任务的释放时机错误会造成泄漏或访问已释放对象。
