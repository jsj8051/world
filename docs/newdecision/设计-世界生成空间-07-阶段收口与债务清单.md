因此本阶段的目标是：把已有边界固定住、把遗留债清掉、把性能基线测出来，然后结束架构设计阶段。

## 1 这一阶段实际走完的证明链

| 步 | 落地 | 证明了什么 |
|---|---|---|
| **2A** | `PrecipitationModel` + `RiverNetwork.RunoffAccum` | 河流可以**独立演化**：World Simulation 有输入、不依赖 Placement |
| **2B** | `RiverGraph` + `RiverGeometry` | 水文事实 / 拓扑事实 / 几何表达**三层可分离**；连续性不必靠改阈值 |
| **2C-A** | `BasinGraph` | 流域可以**独立归类**：`termination ≠ lake` 被真实案例证明（basin26 零容量不成湖） |
| **2C-B** | `LakeState` | 湖泊可以**独立成为状态层**：`Volume ≠ AccumMm`（定义分离 + 数值一致测试） |
| **2C-C** | `WaterTopology` | 水体之间可以**组合**：`RiverGraph` 不需要知道 Lake 存在；四概念不互相吞并 |

**贯穿全程的两条元原则**（各抓到过真实 bug，不是口号）：
1. **退化解原则**：任何新物理量/权重/场进入既有算法，必须有可验证退化解
   （已抓：`BFS label` 没接、`H3Hydrology cellWeight` 没接）。
2. **原子事实优先于分类**：先存原子事实（`DownstreamRiver<0` / `UpstreamCount==0` /
   `TerminatesAtOcean`），再由分类做表现；分类不得覆盖事实（孤立河案例）。

## 2 冻结面（v1，不再扩张）


### 4.3 判读（只写实测能支撑的，不做未经证实的归因）

1. **瓶颈不在水文，在投影与格壳**。res5 全链 58.6 s 中
   `H3LandSeaProjector` 27.1 s（46%）+ `Ball 构造` 9.4 s（16%）+ `HeightComposer` 10.4 s（18%）
   = **80%**；而**整个 World Simulation 栈（降水→河网→图→几何→流域→湖→水系）只占 1.5 s（2.5%）**。
   ⇒ 此前担心的"水系统拖慢生成"**实测不成立**，不需要为水文做任何性能优化。
2. **单格成本随档位上升**（Projector：res1 22.6 µs/格 → res4 5.7 → res5 13.4）。
   res4→res5 格数 ×7、耗时 ×16.4。可能原因是**内存层次**（res5 托管堆 935 MB，
   随机邻居访问退出缓存）而非算法复杂度——**未做采样剖析确认，登记为待查**。
3. **res5 是否进入主流程需要用户拍板**：58.6 s 单次生成 + ~1.1 GB 峰值，
   在当前"生成一次、交互判读"的用法下可接受，**实时重算不可接受**。
4. **值得优化 / 保持现状**：
   - 值得：`H3LandSeaProjector`（唯一绝对大头，且单格成本随规模上升）。
   - 保持：水文栈全部（合计 2.5%）、`RegionalLandforms`/`VolcanoField`/`FinalGeography`
     （各 <2%）、`FinalSpatialIndex`（1%，且目前无消费者——见 D-4）。
   - 不在本阶段：`ClimateFields` 风蚀 O(n²)（旧线，随 D-3 决策）。

### 4.4 ★观测异常（登记，不作为 v1 缺陷修复）

**内流流域占比随分辨率暴涨**：res1 7/158 = **4.4%** → res4 3,765/10,742 = **35.0%** →
res5 31,424/51,128 = **61.5%**（真实地球内流区约占陆地 20%）。
同期成湖率：res4 3,671/3,765 = 97.5%，res5 9,646/31,424 = 30.7%。

初步解释（**未证实**）：格越细，局部起伏保留越多微小洼地；res1 单格 60 万 km² 把这些洼地
平滑掉了。这与 2C-A 实测到的"MinLand 钳制平底退化洼地"（basin26）同族。
**按 §2 防膨胀三问，不为此新增层或机制**——登记为尺度判读问题，
等有真实消费者（文明选址/农业判读）需要用内流比例时再处理。

### 5.2 ★永久原则：新参数先问"本体是拓扑量还是物理量"

> **以后所有涉及"多少格""多远""多大"的新参数，都先问：这个参数的本体到底是
> 拓扑量还是物理量？**
> 若是**物理量**，必须先落到 `km` / `km²` / `km³` / `km³·a⁻¹` **再进入算法**；
> 只有"邻接几跳""环路长度""图深度"这类**真正的拓扑概念**才保留纯格数。

这条钉住后，本轮发现的"面积两套真相源""40 格跨 res 失真""距离公式静态看没问题
但实际错了"这三类问题会大幅减少。已同步写进 §2 冻结面。

### 5.3 ★底层类的固定验收门槛：独立实现逐点对照

> **`SpatialScale` 这类底层基础类，"独立实现逐点对照"是固定门槛，不是一次性测试。**

### 5.5 ★★生产分辨率不得被子系统反向绑架（二次拍板的实质）

初版拍板"生产档 res2"是**倒果为因**，已作废。正确的因果方向是：

```
生产分辨率 = 世界本身的空间离散尺度 = res4（先定，冻结）
        ↓
地质 / 地貌 / 水文 / 火山 / 人文…… 各模拟系统适配这个尺度
```

而不是"看哪个子系统在哪一档表现最好，就选哪一档"。

**核心认定（写死）**：

> **当前水文模型的有效工作尺度集中在 res2 附近，但项目生产分辨率为 res4；
> 因此该差异被认定为模型尺度适配缺陷（D-11），
> 不得通过降低生产分辨率规避。**

否则会滑向一种架构倒退：
`发现某模拟系统在 res4 不工作 → 换成 res3 → 另一个系统不工作 → 换成 res2`
⇒ 最后 res 变成"哪个模块最舒服用哪个"，这是不应该的。

**各档用途**（诊断实验档 ≠ 生产档）：

| res | 用途 |
|---|---|
| res1 | 粗尺度退化测试 |
| res2 | 中尺度行为测试 |
| res3 | 过渡尺度测试 |
| **res4** | **实际生产尺度** |

代码钉子：`WorldGenPlanet.ProductionRes = 4`（编译期常量）+ 测试
`SpatialScaleTests.ProductionRes_IsRes4_Frozen`（改动须用户解冻）。

### 5.6 ★不要为了让 res4 出现更多河流而调 70,800 km²

实测暴露的是**两个不同的问题**，混为一谈就会调错参数：

| | 问题 A · 粗尺度 | 问题 B · 细尺度 |
|---|---|---|
| 现象 | res1 一个格就可能超过河流阈值 | res4 每格 ≈26 km，噪声相关长度 ≈90 km ⇒ 只剩 ≈3.5 格 |
| 链路 | 空间采样太粗 ⇒ 阈值失去判别能力 | 降水/径流空间结构**采样不足** ⇒ 汇流难以跨越足够空间 ⇒ `FlowAccum` 很难达到 70,800 km² ⇒ 河网断裂 |
| 归属 | 诊断档的正常退化表现 | **D-11：必须在 res4 上解决** |

⇒ **调阈值只会把两个问题一起掩盖**：res4 河流变多 ≠ 水文模型变对。
D-11 的正确方向是**让水文适配 res4**，而不是改阈值或降档。
> ⚠️ **2026-10-04 修正**：本行原写"采样密度 / 空间相关长度"。实测（§13.1）表明
> **res4 采样是充分的**（高度场相关长度 ≈ 邻格距的 10 倍），"采样不足"不是原因。
> 当前证据支持的第一根因是**洼地截断**，见 §13.3。

## 7 空间尺度 / 单位层（D-10，2026-10-04，已完成）

> 用户提出并拍板：**这不是"某个算法算错了"，而是整个模拟系统缺少一个统一的
> 空间尺度 / 单位层。** res 只是**离散化精度**，它决定"一个格子多大"，
> **不应该改变任何物理量的意义**。按 §2 防膨胀三问第 3 问（没有消费者 ⇒ 不建层），
> 本层**例外获准**——因为它不是"新世界内容"，而是收口阶段的**基础设施**，
> 且已有真实消费者（Lake/Basin/River/Precipitation 五个系统）。

### 7.1 ★三类参数（此后见到任何参数先问它属于哪一类）

| 类 | 含义 | 典型参数 | 正确单位 |
|---|---|---|---|
| **A 拓扑尺度** | 图上的离散结构 | BFS 距离 / H3 hop / 邻居数 / 图深度 / 成员格数 | `cell` / `hop`（**与 res 强相关，永不跨 res 比较**） |
| **B 几何尺度** | 真实世界的空间大小 | 面积 / 距离 / 山脉宽度 / 河长 / 湖面 | `km` / `km²` / `km³` |
| **C 物理尺度** | 真实世界的物理过程 | 降水 / 蒸发 / 径流 / 水量 / 侵蚀 | `mm` / `mm·a⁻¹` / `km³` |

**res 只决定"一个格子有多大"；物理参数决定"现实世界有多大"；两者不得混用。**

### 7.2 建层前先测：口径混乱的实际规模

探针（`PerfBench --probe`）实测发现，**"一格多大"在同一世界里曾有三套口径**：

| 口径 | 位置 | res1 值 |
|---|---|---|
| H3 平均面积表（硬编码 9 档） | `LakeState.CellAreaKm2(res)` | 607,221 km² |
| 球面均分 `4πR²/n`（内联 3 处） | `GeologicalRegions:119` / `MountainSkeleton:89` / `VolcanoField:70` | 605,777 km² |
| 人文层自己的 `4πR²/N` | `GameGrid:201` | （独立网格，不参与本层） |

⇒ 差 0.24%，**看似小，但它意味着"同一个世界里两套面积真相源"**——
任何跨系统面积比较都可能悄悄用到不同口径。已统一为 `SpatialScale`（§7.3）。

> ★**过程中纠正的一次错误推断**：曾怀疑 H3 `res` 编号与官方偏移一整档（会放大 7 倍），

> 官方 `getHexagonAreaAvgKm2(1)` = 609,788，与等积口径 605,777 差 0.4%，自洽。
> **教训：口径问题必须实测，不能靠"官方文档对照表"推断**（本项目的 `res` 编号

### 7.3 `SpatialScale`（`scripts/noise_world/worldgen/SpatialScale.cs`）

薄层，四个口径各有明确分工，**不合并**（合并会牺牲某个性）：

| 成员 | 口径 | 用途 | 为什么不用别的 |
|---|---|---|---|
| `CellAreaKm2` | **等积** `4πR²/n` | **默认**；所有面积 ⇄ 格数换算 | 选它不是因为最精确，而是 `Σ = 4πR²` **严格守恒**（守恒断言与收敛测试的地基）。H3 逐格精确值围绕它波动（pentagon + 大陆漂移） |
| `ExactCellAreaKm2(cell)` | **H3 精确** | 最终判读 / 渲染 / 精度敏感 | 逐格 native 调用，O(n)；res5 的 200 万格不可全量用 |
| `DistanceKm(a,b)` | **真实大圆**（haversine） | 一切"物理距离" | 唯一跨 res 语义一致的距离。**已验证与 `H3.CellToLatLng` 口径一致（差 <1 m，float 精度）** |
| `HopDistanceKm` / `HopDistanceKmRange` | **有偏近似** | 仅量级表述 / UI 提示 | 实测标定：真实邻格距 / 格边长 = res1 1.78 / res2 1.77 / res3 1.78，逐邻居最大偏差 18.7~28.7% ⇒ **不得用于任何需要真实距离的模拟** |

`AreaConserving` 属性是自检口：`CellAreaKm2 × CellCount == 4πR²` 恒等式。

> ★**实施中抓到自己的 bug（值得留档）**：`DistanceKm` 初版把已算好的弧度又乘了一次
> `d2r` ⇒ 距离缩小 57 倍。**静态看公式完全正常**，是探针的"逐邻居实测"把它照出来的
> （res1 邻格距 88 km vs 期望 837 km）。⇒ **新基础设施层必须配"活体对照"**：
> 不是"公式看起来对"，而是"与独立实现逐点对齐"。

| `BasinGraph` | `Area`（格数） | 新增 `AreaKm2`（**格数保留**，它是拓扑量/收敛判据要用） |
| `RiverNetwork` | `FlowAccum`（格数）+ 40 格阈值 | 新增 `FlowAccumKm2`（**汇水面积 = catchment area**）、`RunoffAccumKm3`（体积）、`RiverThresholdKm2`；阈值双入口（格数 / km²），km² 优先 |
| `LakeState.AreaKm2` / `VolumeKm3` | `float[]` | `double[]`（物理量；`float` 存 605,777 km² 相对误差 5e-8 会让几何一致性断言假红） |

**★退化解成立（已钉测试）**：同一 res 下，格数阈值 `T` 与等价面积阈值 `T×A`
判据**逐格完全一致** ⇒ 迁移零行为漂移。跨 res 时才显出"物理阈值才是尺度无关的那个"。

### 7.5 阈值物理化：`40 格` 在不同 res 下相差 34 倍

| res | 格数 | 每格面积 | `40 格` = 流域面积 |
|---|---|---|---|
| 1 | 842 | 605,777 km² | **2,431 万 km²** |
| 2 | 5,882 | 86,716 km² | 347 万 km² |
| 3 | 41,162 | 12,392 km² | 49.6 万 km² |
| 4 | 288,122 | 1,770 km² | **7.08 万 km²** |

同一个常量，跨 34 倍。新的物理口径 `RiverThresholdAreaKm2 = 70,800 km²`
（黄河量级；res4 下 ≈ 40 格 ⇒ 与旧默认平滑对接，res1 下 1 格即达标）。

> ⚠️ **70,800 km² 是"当前水文模型的工程标定参数"，不是自然常数**（用户拍板 §5.1 E）。
> 它的作用是**与既有 res4 的 40 格行为平滑衔接**，让迁移零行为漂移；
> **它不代表现实世界"河流形成的物理阈值"**。将来出现"可通航河流 / 灌溉水量 /
> 河宽 / 年径流"等真实消费者时，应**重新做物理标定**，而不得把它当成世界规律沿用。

## 8 分辨率收敛（Resolution Convergence）

### 8.1 目标与纪律

**目标不是"每个格一模一样"**（那不可能也无意义），而是
**提高 res ⇒ 宏观统计量趋于稳定**。这是判断"物理参数是否真的与 res 解耦"的唯一手段：
某个量随 res 漂移 ⇒ 要么它本身是拓扑量（该标 cell/hop），要么它的参数写成了格数。

工具：`PerfBench --converge 1 2 3 4`（全链路用物理阈值 70,800 km²）。
测试：`ResolutionConvergenceTests`（跑 res1..res3，res4 人工判读）。

### 8.2 实测读数（seed 42，物理阈值 70,800 km²）

### 8.3 诊断结论（比"单位不一致"更本质）

1. **海陆判定已完全 res 无关**（陆地占比极差 0.44 pp）⇒ 证明 §7 的单位层
   没有引入漂移，也证明 Final 层口径是对的。
2. **过半流域是"单格流域"**：中位流域面积 **精确等于**格面积（四个 res 比值都是 1.000）
   ⇒ 超过一半的流域面积 = 一个格子，**没有物理意义**（一条河至少应有若干格汇水）。
   这是内流占比冲到 35% 的直接原因。
3. **河网随 res 剧烈变化**：河流格占陆地格比例 100% → 81.8% → 12.9% → 0.98%，跨 100 倍。
   **两个独立根因**：
   - ① **阈值在粗网格下失效**：res1 每格 605,777 km² ≫ 阈值 70,800 km² ⇒ 一格即达标
     ⇒ 整块陆地都是河。这**不是"阈值太小"**，是粗网格没有足够空间让阈值生效；
   - ② **噪声相关长度 vs 采样密度不匹配**：`HeightComposer` 三档噪声波长
     5000 / 600 / 90 km **本身是正确的物理量**，但 res1 每格 483 km（90 km 噪声不足 1 格），
     res4 每格 26 km（90 km 噪声仅 3.5 格）⇒ 汇流累积在细网格上攒不到阈值 ⇒ 河网断链。
4. **D-10 本身是有效的**：改用物理阈值后，"陆地占比收敛"这一条立刻成立，
   说明尺度层方向正确；剩下的不收敛是**噪声尺度问题**，不是**单位问题**。

### 8.4 ★这组数据证明了什么、没证明什么

**证明了**：水文层存在**尺度适配问题**（这是本轮实验的真正价值）。
**没证明**：应该生产 res2（这是初版拍板的误读，已由用户二次拍板纠正，§5.5）。

| res | 当前水文表现 | 档位定位 |
|---|---|---|
| res1 | 阈值基本失去意义，河网严重饱和 | 粗尺度退化测试 |
| res2 | 仍能形成连续水文结构（**但**河流格占陆地仍有 81.8%） | 中尺度行为测试 |
| res3 | 河网明显稀疏 | 过渡尺度测试 |
| **res4** | 大量断链，阈值与采样密度失配 | **实际生产尺度（冻结）** |

⚠️ 三点限定：
1. **res2 不是"收敛平台"**——它的河流密度 81.8% 依然过高，当前形态是
   「饱和 → 还能工作 → 快速变稀 → 断链」的**单调斜坡**，不存在收敛区。
2. **不得**写成"实验已证明 res2 是最佳分辨率"或"水文特征分辨率"。
3. **生产档 = res4 冻结**（§5.5）；res2 只是**当前水文模型的诊断参考尺度**。

**统一表述（全库文档强制）**：
- ✅ 生产分辨率 = **res4**；水文模型的**有效工作尺度集中在 res2 附近**
- ✅ 该差异 = **模型尺度适配缺陷（D-11）**，**不得通过降低生产分辨率规避**
- ⛔ ~~生产基准档 res2~~ / ~~特征分辨率~~ / ~~收敛分辨率~~

### 8.5 处置路径（用户拍板 G）

**不为收敛本身去调参。** 把 `100% → 81.8% → 12.9% → 0.98%` "调漂亮"很容易得到一个
**伪收敛系统**。正确路径是：

```
当前实现 → 记录真实缺陷 → 特征测试锁住现状 → 解决 D-11
        → 重新跑 res1~res4 → 再决定收敛断言
```

这比现在硬定义一个 `riverDensity ≈ constant` 健康得多。
当前两条缺陷（单格流域、河网断链）以**特征测试**（characterization test）钉住现状，
注释标明"这是缺陷跟踪，修好后本测试会红并提醒改写为收敛断言"。

只有当出现真实消费者（文明选址需要"可通航的河"、农业需要"灌溉水量"）
才会重新评估阈值——那时"多大算一条河"才有明确答案，
且**重新标定后的值仍然不是自然常数**（§5.1 E）。

### 10.7 ★本轮沉淀的三条范式（超出 D-3 本身，适用于后续所有架构工作）

#### 10.7.1 契约三件套：**结果 / 方向 / 边界**（用户 2026-10-04 认定为 v1 架构契约设计范式）

单独一条 architecture contract 不够。三条同时存在才有封闭性：

| 维度 | 钉什么 | 缺了会怎样 |
|---|---|---|
| **结果** | 某个类型/命名空间在程序集里**已不存在** | 只钉方向 ⇒ 旧东西**复活也测不出来** |
| **方向** | A 不得引用 B | 只钉结果 ⇒ **防不住重新耦合** |
| **边界** | 保留者的**依赖白名单** | 缺了 ⇒ 生成能力可以偷偷塞回消费者 |

> 一句话：**只钉方向不钉结果，旧链复活测不出来；只钉结果不钉方向，防不住重新耦合。**
> 后续任何"清退 / 隔离 / 分层"类改动，都按这三问配齐契约，而不是只加一条断言。

#### 10.7.5 ★★先定**维数**，再选统计量（D-11 收口沉淀；用户 2026-10-04 指定为通用原则）

> **不先确定特征是 0D / 1D / 2D，就无法判断"跨分辨率是否稳定"。**
> 用错维数的统计量会**制造出根本不存在的"不收敛"**。

**D-11 实证（§13.14）**：河流是 **1D 线特征**，却一直用 **2D 的"河流格占陆格 %"**
做收敛判据 ⇒ 该比例必然 ∝ 格间距、随 res 升高而下降。实测 res3/res4 下降比
**2.434**，理论格间距比 **2.646**，**符合度 92%**；换成 **1D 的"河长密度"
（km 河长 / km² 陆地）**后 ⇒ **0.920（差 8.7%）**。

⇒ **那个"2.43× 的模型失效"是统计量造出来的，不是模型造出来的。**

**沿用表**（后续每个特征下结论前，先填这一行）：

| 特征 | 维数 | 应该用的跨 res 统计量 | **不该**用的 |
|---|---|---|---|
| 火山 / 锚点 | **0D 点** | 个数、个数密度（个 / 10⁶ km²） | 占格 %、覆盖面积 |
| 河流 / 山脉脊线 / 海岸线 | **1D 线** | **总长度（km）**、线密度（km / km²） | 占格 % |
| 湖泊 / 陆块 / 区域 | **2D 面** | 面积（km²）、面积占比（无量纲，**可直接跨 res 比**） | 格数 |
| 水量 / 体积 | **3D 体** | 体积（km³） | 格数加权和 |

**判据三步法**：
1. **定维数**：这个特征在世界里是点 / 线 / 面 / 体？
2. **选同维统计量**：0D→计数、1D→长度、2D→面积（2D 的"占比"本身就无量纲，可直接比）。
3. **再谈收敛**：只有同维统计量下的残差才是真残差；否则先怀疑自己量错了。

⚠️ **反面警示**：D-11 前两层都在"模型有 bug"的框架里找，直到第三层才发现是**量纲**问题。
⇒ **看到跨 res 差 N 倍时，先做维数检验（实测比 vs 格间距比），再怀疑模型。**

#### 10.7.6 ★诊断指标不进生产（防膨胀三问的边界情形）

第三层诊断需要一个"河长密度"指标，但**唯一的消费者是诊断探针**。
⇒ **不新增 `RiverLengthKm` 生产字段**；改为在 `--d11` 里由既有事实现场算出：

```
河长      = 河流格数（IsRiver 掩码）× 相邻格中心距（√3 × SpatialScale.CellEdgeKm）
河长密度  = 河长 / 陆地面积（陆格数 × SpatialScale.CellAreaKm2）
```

⇒ **判别标准**：一个量要不要升格为生产字段，看**有没有真实消费者**，
不看"算出来好看"。诊断指标留在诊断工具里，是**正确的归属**。

### 13.2 ★新缺陷 D-14：降水模型的海岸加权**完全失效**（字段用反了）

`FinalGeography` 的两个 BFS 字段语义：

② 注释写的是"临海多雨、**内陆衰减**"，对陆格有意义的只有"离岸距离"；

**① `RunoffAccumKm3` 单独作判据怎么样？（用户重点问题之一）**

**结论：在不动阈值的前提下，它是现行判据的恒等改写，改善为零。**
- 数学恒等：`RunoffAccum ≥ meanP·(70800/cellKm2)` ⟺ `RunoffAccumKm3 ≥ meanP·70800/1e6`。
- 实测吻合：C1 阈值换算 = **100.3 km³/a**（且**跨 res 恒定**：102.7 / 100.9 / 100.3 / 100.3，差 2.4%）；
  C3 @100 km³/a 给 **2.405×** vs C1 **2.407×** —— 逐位吻合。
- 而 C3 在**别的**阈值上会明显跑开：@3 km³ 1.631×、@10 km³ **3.315×**、@30 km³ 2.754×、
  @300 km³ 2.539×、@1,000 km³ 2.871×。
  ⇒ **纯水量判据没有"天然稳定点"**；它看起来更好或更差，只是阈值选取的结果。
  ⇒ 要让它有区别，就必须**重新标定 km³ 阈值**——这正是用户明确推到下一步的事。

**② 面积 + 水量双条件是否明显稳定？（用户重点问题之二）**

**结论：不明显。C4 = 2.437×，与 C2 的 2.434× 差 0.1%。**
- 原因（6.5）：**`ln(汇水面积)` 与 `ln(累积水量)` 的 Pearson r = 0.977（res4）/ 0.970（res3）**。
- ⇒ 水量 ≈ 面积 × 一个缓变的降水因子，**几乎不携带独立信息**；第二个条件只砍掉
  C2 中的 15.6%（`C2∧¬C1`，"够大但太干"），且砍掉的那部分在两个 res 上比例几乎相同
  （15.47% vs 15.57%）⇒ 对比值**没有微分效应**。
- ⇒ **"足够大的汇水范围 + 足够大的累积水量"听起来更有架构价值，但在这个降水场下它等价于
  只要求汇水范围。**（除非降水场有真正的空间结构——将来 Climate Simulation 上线后值得重测这一条。）

### 13.14 ★★第三层的真正根因：量纲用错了——**河流是一维线特征**

6.6 维数检验（河长 = 河流格数 × 相邻格中心距，即每格代表一段中心到中心的河段）：

| 量 | res1 | res2 | res3 | res4 | res3/res4 |
|---|---:|---:|---:|---:|---:|
| 陆格数 | 246 | 1,733 | 11,992 | 83,603 | — |
| 格间距（km） | 836.4 | 316.4 | 119.6 | 45.2 | **2.646** |
| C2 河流格数（绝对） | 246 | 1,733 | 2,392 | 6,852 | 0.349 |
| C2 **河长**（km） | 205,744 | 548,382 | 286,128 | 309,796 | **0.924** |
| C2 **河长密度**（km / 10⁶ km² 陆地） | 1,380.6 | 3,649.1 | 1,925.5 | 2,093.2 | **0.920** |
| C1 **河长密度**（km / 10⁶ km²） | 1,380.6 | 2,758.4 | 1,677.6 | 1,843.9 | **0.910** |

**判读**：
- 河流是 **1D 线特征**。同一条河网在更细网格上，覆盖的格数占陆格的比例 **∝ 格间距**。
  ⇒ "**河流格占陆格 %**" 这个统计量**必然**随 res 升高而下降，下降比 ≈ 格间距之比。
- 实测：占陆格% 比 = **2.434**，理论格间距比 = **2.646** ⇒ **符合度 92%**。
- **换成"河长密度"口径后，res3/res4 从 2.43×（差 143%）降到 0.920（差 8.7%，即 1.087×）。**
- ⇒ **2.43× 不是模型缺陷，是拿面积型统计量去量一维特征造成的口径错误。**

**剩下的 8.7% 是什么**：res4 比 res3 多解析出 8% 的河长（309,796 vs 286,128 km）。
这是**河网的分形性**——更细的网格分辨出更多低级别支流，总河长随解析尺度缓慢增长。
这是物理上应有的行为（真实河网也是分形的），**不是 bug**；要真正收敛必须定义
"最小河流的物理标准"（这正是 70,800 km² 目前充当的角色）。

## 13.18 河流表现冻结（2026-10-04）：只做"符号粗细系统"，不表达物理河宽

### 冻结定义（一句话）

> **生产档河流 = res 无关的连续中心线 + res 绑定的 H3 覆盖索引 + 屏幕空间符号宽度；当前不表达物理河宽。**

### 为什么不做"河宽系统"（实测）

| 200 m（大河） | 0.8% | ≈0.017 px |
| 10 m（小溪） | 0.04% | ≈0.0009 px |

⇒ 真实河宽在 res4 是**彻头彻尾的亚格量**。写 `WidthM` / `DepthM` / 河岸真实几何 / 河漫滩 / 分汊 / 岛屿
= 编造一个连亚格都算不上、且**无法被任何判据证伪**的几何量。
⇒ **没有真实近景消费者前，LOD 2/3 整条链不建；架构根本不承诺真实河宽。**
不是"先留个接口以后实现"。将来真出现局部高倍缩放 / 城市级地图 / 河谷可视化时，重走：
消费者 → 所需空间分辨率 → 数据源是否足够 → 是否需要局部高 res → 是否需要独立河流矢量 → 是否需要真实宽度模型。

### 符号宽度设计

- **宽度属于河段（segment），不属于节点**：河段累积量 = **上游格**的 `AccumMm`；
  `NodeKind` **只决定颜色**（干流/支流）与河口打点，**不参与粗细**。
  ⚠️ 若让 NodeKind 参与粗细，单调性会破缺——小干流的河源与大支流的河口会反转。
- **离散 5 档，分位断点** p50 / p75 / p90 / p98 → `StrokeWidthPx = {0.9, 1.3, 1.9, 2.7, 3.8}`。
  **不做连续映射**（避免 1.37 / 1.42 / 1.51 px 这种看起来像噪声的抖动）。
- **参考口径**：全球远景视图下星球直径 1000 px；换算 `半宽 = px × Radius / 1000`。
  ⚠️ 不是"恒 px"——真恒 px 需要 shader，当前无消费者。
- **与真实河宽的落差**（球半径口径）：800 m = 1.26e-4 R；Class 0 全宽 1.8e-3 R（**14×**）、
  Class 4 全宽 7.6e-3 R（**61×**）⇒ 符号笔画比真实河宽大 1~2 个数量级，
  **绝不可当作米数用于任何水文 / 流量计算**。
- **分位而非固定阈值**：免标定、不随降水模型量级漂移；代价是档位含义是"本世界内的相对等级"。

### Resolution 契约（有测试钉死）

```
RiverGeometry
├── Lines      = 单位球心方向向量  → res 无关（可叠加到任意 res 的地表网格）
└── LineCells  = H3 格索引        → 仅对生成它的 res 有效（新增 SourceRes 记录绑定）
```

⚠️ 别把"河流不绑 res"理解成"res 无关的 RiverGraph"：**汇流累积定义在 H3 邻接图上，
换 res 河网结构必变**，res 无关的河网是做不到的。
能守住的是"生产档 res4 冻结 ⇒ 河网事实唯一，表现层只读不重算"。

### River v1.2（2026-10-04 产品拍板）：Camera-aware Symbol Width

**产品契约（一句话）**：

> 生产河流支持**全球至区域级**地图缩放；河流宽度**始终**是视觉符号宽度、而非物理河宽，
> 并在正式支持的缩放范围内做**相机感知补偿**；**超出该范围不承诺近景河道表现**。

正式支持 = **区域级战略地图的观察/操作**，**不是**"可无限放大到真实河道尺度"。
⇒ 不引入：真实河宽 / 局部高分辨率水文 / screen-space shader ribbon / 河流动画。

#### 为什么叫 Camera-aware 而不叫 LOD

没有换几何语义、没有换数据、没有换 LOD 档——只是同一个 River Symbol 根据 camera scale
调整**表现宽度**。叫 LOD 会暗示"LOD0→LOD1→LOD2 换数据"，那是假的。

#### 公式

```
zoom  = uRef / uNow          （uRef = 参考视图的"世界单位/像素"；zoom=1 ⇒ 全球远景参考视图）
comp  = clamp(zoom^(Alpha−1), CompMin, 1)         Alpha=0.35，CompMin=0.5
worldWidth = SymbolWidth × Radius / 1000 × comp
```

`Alpha = 1` ⇒ 恒 px（要 shader）；`Alpha = 0` ⇒ 世界空间固定（v1 行为，会失控）。取 0.35 = **部分补偿**：既不失控，也不假装自己是恒 px。

★**单向依赖**：`Camera → 表现参数 → RiverLineOverlay`。绝不反向污染 `RiverGeometry` / `RiverGraph`，更不会"zoom 越近就重算河网"。生产水文事实完全冻结。

#### 实测曲线（补偿后屏幕像素 = StrokeWidthPx × zoom × comp）

| zoom | comp | 补偿后相对宽度 | v1.1 无补偿 |
|---|---|---|---|
| 1.0（全球） | 1.00 | **1.00×** | 1.00× |
| 1.56（区域） | 0.75 | **1.17×** | 1.56× |
| 2.51（近区域） | 0.55 | **1.38×** | 2.51× |
| 3.0 | 0.50（触底） | 1.50× | 3.00× |
| 8.0（支持上界） | 0.50（触底） | 4.00× | 8.00× |

曲线正好穿过用户给的参考点（区域 ×0.75 / 近区域 ×0.55）。
⚠️ zoom ≳ 3 后 comp 触底 ⇒ **补偿停止、宽度恢复线性增长**，这正是"超出范围不承诺近景表现"的边界行为。

**⚠️ 待标定**：`MinSupportedZoom(0.6)` / `MaxSupportedZoom(8.0)` / `ZoomAlpha(0.35)` / `CompMin(0.5)`
目前是按目标点反解出来的**占位值**，尚未在实机上量出区域视图的真实 zoom 范围。
标定 = 改这 4 个常量（补偿是纯函数，改常量即可，不动结构）。

#### v1.1 顺手钉死：`nextOf` 不得静默覆盖

去重本身正确，但 `nextOf[a] = b` 的"覆盖"会把**拓扑错误**吞掉：
`A→B` 后面又来 `A→C`，最后一个赢 ⇒ 不是去重，是掩盖。

现改为 `TryAddEdge`：
- 同一条边重复 ⇒ **正常去重**（这正是干流被多条 source→outlet 路径共有时的预期行为）
- 同一上游出现不同下游 ⇒ **冲突计数 + 保留首条**，挂到 `RiverLineOverlay.TopologyConflicts` 暴露

#### v1.2 新增护栏

| 测试 | 钉什么 |
|---|---|
| `TryAddEdge_DuplicateIsDedup_ConflictIsExposed` | 重复边不算冲突；**冲突必须计数且保留首条** |
| `Chains_CoverEveryRiverEdgeExactlyOnce`（增强） | 真实河网 `conflicts == 0` |
| `ZoomCompensation_IsBoundedAndMonotone` | zoom=1 ⇒ 1；值域 [CompMin,1]；随 zoom 单调不增 |
| `ZoomCompensation_ClampsOutsideSupportedRange` | 超范围停在边界值；非法输入退回 1（不产生 NaN） |
| `ZoomCompensation_ShrinksButDoesNotPretendConstantPx` | 拉近必须变细，但不得细于 CompMin 比例 |

### River v2.0（2026-10-04 立项）：Presentation Spline + River Surface Shader

**为什么不是 v1.3**：v1.x 再怎么加 join/bevel/corner smoothing，都是在"把六边形折线伪装成 spline"——
中心线仍然只有 6 个方向。v2 是**层级切换**：H3 河网当**控制数据**，表现层另生成连续样条，
再交给独立的 river surface shader。

#### 职责三分

```
HYDROLOGY FACT                      RiverNetwork / RiverGraph / WaterTopology / RiverGeometry（一律不动）
        │
        ▼  Chain（edge 去重，一条 edge 只进一个 chain）
RiverPresentationSpline             ★表现层：穿过每个 H3 锚点的 constrained spline
        │
        ▼  自适应采样
RiverSurfaceMesh（一份主几何）
        │
        ▼
RiverSurfaceShader                  屏幕空间恒 px 宽度 + 横截面柔化 + 水色
```

#### ① 样条：Centripetal Catmull-Rom，**穿过**锚点

- 不是最小二乘拟合、不是 B 样条近似 ⇒ `Spline(Pi) = Pi` 数学上精确成立，河道**不会被拽走**。
- 选 **centripetal（α=0.5）**而非 uniform：H3 路径是"长段→短段→急弯→长段"的**非均匀点距**，
  uniform CR 在这种点距下会过冲 / 打环，centripetal 不会。
- 球面处理：R³ 里插值后 `normalize()` 回单位球（在锚点处 normalize 是恒等 ⇒ 不破坏穿过性）。
- ★**最大视觉偏移护栏**：偏移 ≤ 锚点间距 × `MaxDeviationRatio(0.15)`，超界按比例拉回
  ⇒ 平滑只是**去锯齿**，不是重新规划河道。

#### ② 自适应采样：直线 1 段，急弯最多 6 段

`SampleCount = clamp(1 + round(转角落/(π/12)), 1, 6)` ⇒ 全球远景不浪费三角形，区域视图才加密。

#### ③ Shader：一份几何取代 v1.x 的三套共面 mesh

`shaders/river_surface.gdshader`：顶点在 shader 里沿**屏幕空间**展开
（中心线 + `side` 辅助点分别投影，取屏幕方向作为加宽方向）⇒ **恒视觉宽度**。
片元按横截面 `v ∈ [-1,1]`：`|v| < 0.62` 主水面 → `1.0` 完全淡出 ⇒ **软边不再是第二套几何**，
拐角白块 / z-fighting 从根上消失。边缘只做**同色系轻微提亮**（`u_edge_gain = 1.16`），绝不是白边。

**顶点属性约定**：`VERTEX`=中心线点（同点 emit 两个顶点）、`NORMAL`=球面横向 `side`、
`UV.x`=沿河弧长参数（备用）、`UV.y`=横截面 ∓1、`COLOR.rgb`=水色、
**`UV2.x`=目标宽度（px）**。

> ⚠️ **不能走 `COLOR.a` 传宽度（2026-10-05 引擎内实测踩坑）**：Godot 内部会把顶点色 alpha 夹到 `[0,1]`，
> 0.9~3.8 px 全被截成 1.0 ⇒ 河流退化成 1px 细线，5 档宽度系统静默失效。已改用 `UV2.x`（vec2 浮点，无值域限制）。

#### ④ 宽度体系：当前**统一最粗档**（2026-10-04 用户视觉决策）

`Accumulation → p50/p75/p90/p98 → Class 0~4 → StrokeWidthPx` 的**分档能力保留**
（纯函数、零副作用，仍被 v1.x 兜底路径的 `HalfWidthWorld` / `SoftHalfWidthWorld` 消费，不是死代码）。

但 **v2 屏幕空间路径当前固定取最大档**（`RiverSymbolWidth.UniformWidthPx = 3.8 px`）——
用户决策："一直是最大号的粗度就行"。将来要恢复"粗细表达径流量"，只需把渲染处换回 `StrokeWidthPx[cls]`。
`SymbolWidth ≠ PhysicalWidth` 契约不变。

> **2026-10-05 引擎内实测**：
> - 标定档（强制所有顶点 `UV2.x = 8px`）：res3 实测 `6.71 / 6.41 / 6.54 px`，res4 实测 `6.85 / 7.13 / 7.08 px`，
>   zoom 从 1.10 拉到 1.79（+62%）时宽度变化 < 5% ⇒ **恒 px 验证通过**。
> - 默认档（5 档分类）：res4 全球/区域/近景平均 `1.13 / 1.20 / 1.59 px`，差异来自**可见河段的档位构成**（近景只看到局部主干），
>   不是渲染宽度随 zoom 变化。
> - 主场景 OrbitalCamera 实际可及 zoom 范围约 **1.10 ~ 1.79**（默认远景 1.7R ⇒ zoom≈1.10，最近贴地 1.02R ⇒ zoom≈1.79），
>   原先 `ZoomCompensation` 的 `[0.6, 8.0]` 范围大部分是死区间，不是实际可达范围。

#### ⑤ ★河流贴地：深度层次改由 **NDC 偏移**提供，不再物理抬升（2026-10-04）

**问题**：旧实现把河线物理抬到 `R × 1.0030~1.0065`，在 R=2（≈6371 km）下 = 离地 **19 / 25 / 41 km**。
危害不只是"看起来粗"——**掠射角下抬升量会换算成很大的横向屏幕位移**，河线明显偏离真实河道。
实测河线相对地表的屏幕位移（中位 / P90，px）：

| 视图 | 旧 lift=1.0040 | 新（几何贴地） |
|---|---|---|
| 全球 1.7R | 3.60 / 4.50 | **0.00 / 0.00** |
| 区域 1.15R | 23.41 / 32.66 | **0.00 / 0.00** |
| 近景 1.05R | **55.22 / 100.58** | **0.00 / 0.00** |

**做法**：v2 屏幕空间路径的几何 **lift = 1.0（完全贴地）**，干流/支流/河口的层次改由 shader 的
`POSITION.z += UV2.y * POSITION.w`（NDC 深度偏移）提供——**只改 z，不改 x/y ⇒ 零视差**。

**两个实测踩坑（勿改回）**：

1. **方向是 `+=`**：Godot 4 的 RenderingDevice 在 D3D12/Vulkan 下用 **reversed-Z**（近大远小）。
   写成 `-=` 时实测墨水从 26523 暴跌到 7446（河线被地形遮住）——这就是判别方向翻错的方法。
2. **bias 量级必须实测扫参**：解析式估算给 `1e-6`，实测只有 2.26px 宽（被地形吃掉 ~28%）；
   `1e-5` → 3.20px（近景仍差 12%）；**`1e-4` → 3.25px 饱和**（与 `1e-3` 完全一致 ⇒ 再大无收益、也不穿透）。
   取值：支流 `1e-4` / 干流 `2e-4` / 河口 `3e-4`。

v1.x **兜底路径没有 shader**，仍用物理抬升（已同步压到 `1.00020 / 1.00030 / 1.00060`，比旧值小 15×）。

| 路径 | 触发 | 说明 |

| **WorldSpace**（兜底） | shader 缺失，或 `UseScreenSpace = false` | v1.2 camera-aware 世界宽度 ribbon + `StandardMaterial3D` |

#### ⚠️ 实测抓到一个真 bug（已被测试钉死）

**`0 × ∞ = NaN`**：控制点重复（端点曾直接复用 `anchors[m-1]`）使节点步长取 `1e-9`，
而 `t2 ≈ 0.168` 在 float32 下分辨率约 `1.2e-8` ⇒ `t2 + 1e-9` 被舍入成 `t2` 本身
⇒ `t3 - t2 == 0` ⇒ 除零得 ±∞ ⇒ `(p3-p2)·∞ = 0×∞ = NaN`，**整段采样点全变 NaN**。

修法不是加大那个绝对下限，而是**消除重复控制点**（标准 CR 端点处理：反射虚拟控制点
`p0 = p1 + (p1-p2)` / `p3 = p2 + (p2-p1)`），另加两道保险：节点必须严格递增（否则退回弦上线性插值）、
结果非有限则退回弦。

### Ribbon 球面几何：横向向量语义（实测确认 + 极端 case 钉死）

**质疑**：`cross(d1, d2)` 直觉上是"大圆平面的法向"，未必是河流的横向。

**实测结论：两者是同一个向量**（`RiverLineOverlay.SegmentSide` 注释 + `RiverRibbonGeometryTests` 7 项）：

设 θ = d1→d2 的圆心角，t̂ = d1 处沿大圆的单位切向：

```
d2 = cosθ·d1 + sinθ·t̂
cross(d1, d2) = sinθ · cross(d1, t̂)
⇒ normalize(cross(d1, d2)) = cross(d1, t̂) = cross(p, tangent)
```

它同时满足 ① ⊥ d1（径向）⇒ **贴着球面**；② ⊥ t̂（流向）⇒ **垂直于河段**。
关键在于**大圆平面过球心** ⇒ 其法向必然垂直于径向 ⇒ 该法向本身就在切平面内。
"大圆平面法向"与"球面横向"在球面上是同一个向量的两个名字。

**⚠️ 实测中发现并修掉一个真 bug**：旧退化判据 `LengthSquared() < 1e-12` 等价于
"圆心角 < 1e-6 rad 即跳过"。res4 邻格角距 = 7.1e-3 rad（余量 6 个量级）看不出问题，
但**更高 res 的合法短河段会被静默丢掉**（河线出现空洞）。现改为判**长度** `len < 1e-9`
（float32 叉积有效位下界），并补了"短河段不得被丢弃"的回归钉子。

| 极端 case | 钉什么 |
|---|---|
| 直线 | 各段横向必须是**同一向量**（1−eps 内）⇒ ribbon 不摆动、宽度不缩 |
| 等宽性 | 四边形上游/下游边 = 2×半宽×半径，**与曲率、档位无关** |
| 急弯（精确 90°） | 两段横向必须近似正交（数学上严格 = 0）⇒ ribbon 跟着河流转 |
| 接近极点 / 跨极点 | 不得退化、不得 NaN；极区连续折线全程合法 |
| 短河段（1e-3 ~ 1e-7 rad） | **不得被丢弃**（旧代码的回归钉子） |
| 两点河段 | 单段四边形仍等宽、不退化成一点 |
| 退化段（重合 / 反向 180° / 零向量） | 必须返回 false 且 out = Zero，绝不产生 NaN |

## 13.19 表现层通用渲染规范（2026-10-04 用户拍板）：分层 ≠ 沿法线抬起来

### ★最终规则（一句话，以此为准）

> **地图表现层不得通过 world-space radial lift 实现图层排序；需要分层时，几何保持真实表面位置，
> 排序通过 depth / NDC bias、stencil 或专用 overlay pass 实现。**

这一条同时解释三件事：河流为什么不能随意抬高、Cell highlight 为什么不能 `R * 1.0005`、
将来其它地图 overlay 为什么也不能这么干。已从一次 bug 修复升格为**渲染规范**。

### 起因：连续两次踩到同一个病

| 现象 | 实现 | 实测后果 |
|---|---|---|
| 河流"浮在表面上" | 河线抬到 `R × 1.0030~1.0065` | 近景 1.05R 河线偏离河道 **55 px**（中位） |
| 选中格"和实际有点偏差" | 高亮扇面抬到 `R × 1.0005` | 最近视距 1.02R 屏幕边缘偏离 **17.3 px**（≈10% 格宽） |

两者**不是**各自独立的 bug，而是同一个错误的两次实例化：**用 world-space radial lift 做图层分层**。

### ★项目级规则（新增，永久）

```
World Geometry            必须贴真实地形表面
        │
        ▼
Rendering Order          分层**不允许** radial lift
        │
        ├── depth bias（NDC / clip-space Z 偏移）   ← 首选
        ├── polygon offset
        ├── stencil / overlay pass
        └── ❌ position += normal * epsilon（除非该偏移本身是有意义的真实几何）
```

**"图层分层"不等于"把整个图层沿法线抬起来"。** 抬升在掠射角下换算成横向屏幕位移
（`displacement ≈ f · δ · ρ · d / z_view²`，随屏幕半径与视距剧烈变化），
而 NDC/clip-space Z 偏移**只改深度、不改 x/y ⇒ 视差恒为 0**。

### 选中高亮改造（R 上的球面环带）

| 项 | 旧 | 新 |
|---|---|---|
| 几何 | 整格扇面（`AddCellFan`，含格心顶点） | **闭合环带**（`AddCellRing`，2m 顶点 + m 四边形，**无格心顶点、无共面填充**） |
| 半径 | `R × 1.0005` | **`R`** ⇒ `distance(顶点, 地形) = 0` |
| 厚度来源 | 物理抬升的副作用 | shader 沿**切向**在屏幕空间展开（恒 px） |
| 分层 | 抬升 | `UV2.y` → `POSITION.z += bias · POSITION.w`（bias = `4e-4`，> 河流最粗档 `3e-4`） |

**顶点属性契约与 `river_surface.gdshader` 完全一致**（两条表现共用同一套协议）：

| 通道 | 含义 |
|---|---|
| `VERTEX` | 角点方向 × **R**（内外轮廓同位置） |
| `NORMAL` | 角点**切平面内**的内角平分线单位向量（指向格心） |
| `UV.y` | ∓1 ⇒ shader 在屏幕空间向内外各展开半个宽度 |
| `UV2.x` | 目标屏幕宽度（px）★不可走 `COLOR.a`（会被夹到 `[0,1]`） |
| `UV2.y` | NDC 深度偏移 |
| `COLOR` | 高亮色 |

★**miter 补偿**：沿内角平分线偏移 `h` 时，垂直于边的净宽度 = `h·cos(π/m)`
（两端垂距相同 ⇒ 外边界与边平行 ⇒ 整条边等宽、转角**不会**变细），
故预写 `UV2.x = widthPx / cos(π/m)`。正 m 边形下"角点径向"恰好是内角平分线 ⇒ 天然 miter 接头。

### 实机实测（`CellHighlightDiag`，生产档 res4，2560×1440）

| 相机 | 屏幕位置 | 宽(px) | 逐边离散 | 缺口 | 离界(px) | 旧 lift 视差(px) |
|---|---|---|---|---|---|---|
| 1.15R | 中心→边缘 | 2.96–2.97 | 3.9–7.5% | 0 | 0.022–0.042 | 0.10–2.18 |
| 1.05R | 中心→边缘 | 2.96–2.97 | 1.8–3.6% | 0 | 0.007–0.010 | 0.87–6.34 |
| **1.02R** | 中心→边缘 | **2.97** | 1.4–2.0% | **0** | **0.003–0.007** | **5.34–17.28** |
| 1.70R | 中心→边缘 | 2.71–3.02 ⚠️ | 8.3–26.2% | 0 | 0.137–0.198 | 0.007–0.58 |

- **宽 2.96–3.02 px（目标 3.0）在 4 档视距 × 3 屏幕位置全部一致** ⇒ 恒 px 成立。
- **离界 = 墨迹到真实地形边界的带符号平均距离**：新方案 `0.003–0.198 px` ⇒ 轮廓始终贴在边界上。
- ⚠️ 1.70R 三档格子只有 23–35 px 周长，六条边的墨水互相重叠 ⇒ 宽度被系统性低估，已自动标记，非缺陷。

#### ★方法学：质心偏移不能用来判定"有没有浮起"

径向缩放近似等于"以屏幕中心为原点的**均匀放大**" ⇒ 六边形各角向外**对称**位移，
质心几乎不动。实测旧方案在 1.02R 中心档质心只偏移 1.21 px，而角点真实位移 14.10 px（差 12×）。
⇒ 必须用**带符号离界距离**或**角点 unproject 位移**，不能用质心。

### 实测踩坑（诊断开发过程中，勿重犯）

1. **`--headless` 取不到帧**：dummy 渲染服务器下 `GetViewport().GetTexture().GetImage()` 返回
   null（`texture_2d_get ... servers/rendering/dummy`）⇒ 截图类诊断必须**开窗口**跑。
2. **洋红差分单通道公式不可靠**：`α = [(fg.R−fg.G)−(bg.R−bg.G)]/[1−(bg.R−bg.G)]` 在偏红地形上分母趋零，
   把 α 放大到几十 ⇒ 墨迹质心被拖飞 733 px。改为**取分母最大的颜色通道**
   （R：`1−bg.R` / G：`−bg.G` / B：`1−bg.B`），并把 α 夹到 `[0,1]`（α 是覆盖率）。
3. **shoelace 质心漏乘 0.5**：`A += cross` 累加的是 **2×面积**，代 `1/(6A)` 前必须 `A *= 0.5`，
   否则质心整体变成真实值的一半（那 733 px 偏移的真凶）。
4. **质心要用像素中心 `x+0.5`**：用整数像素坐标会引入 `(−0.5,−0.5)` 常量偏置 = **0.707 px**。
5. **软边会让"宽"低估**：横截面 `|cross|<u_core` 实心、core→1 淡出 ⇒ 平均 α = `(1+u_core)/2 = 0.925`
   ⇒ 目标 3.0 px 只量到 2.74 px。除以该系数后回到 2.96 px。
6. **不能按"可见球冠/地平线"角度摆位**：近距离下**视锥**远窄于地平线（1.05R 时冠 0.5 已出屏）
   ⇒ 必须按**目标屏幕半径**二分定位。

### 三个概念彻底分离（本次收口的实质）

```
Cell corners
     ↓
R 上的真实地形轮廓          → 几何位置偏移 = 0
     ↓
screen-space expand         → 视觉宽度偏移 = 屏幕空间（恒 px）
     ↓
NDC depth bias              → 渲染顺序偏移 = clip/depth
```

旧实现把这三者压成"沿法线抬起来"一个自由度 ⇒ 抬高必然同时改变位置、宽度和顺序，
而其中"位置"的改变在掠射角下就是视差。分离之后，改宽度不会动位置、改层次不会动位置。

### 测量方法学统一（取代"肉眼截图诊断"）

| 判据 | 度量 |
|---|---|
| **贴地性** | **带符号离界距离**（墨迹到真实地形边界，笔画跨在边界上正负对称 ⇒ 0） |
| **屏幕恒宽** | 投影墨水 / 投影长度（`projected ink / projected length`） |
| **确定性** | 两帧空场差分噪声底（`frame diff noise floor`） |

⚠️ **质心偏移已废除**：径向缩放 ≈ 以屏幕中心为原点的均匀放大 ⇒ 各角对称外移、质心几乎不动
（实测旧方案 1.02R 中心档质心只 1.21 px，角点真实位移 14.10 px）。**"质心偏移 ≈ 0"不能作为贴合判据。**

### 关键设计点（诊断层代码，不进生产）

1. **双色探针**（支流面=洋红(1,0,1)，干流面=黄(1,1,0)）：
   - 两色 R 通道均为 1，可直接用 R 通道恢复 α：
     `α = (fg.R − bg.R) / (1 − bg.R)`。
   - A/B 实测：`--blend=lin`（先把 sRGB 字节反编码到线性再解 α）会把"相对期望剖面的缺失"从 0.01~0.12 px 抬到 0.08~1.68 px ⇒ **本渲染目标的 alpha 混合是在编码空间完成的**（D3D12/Vulkan 对 UNORM_SRGB 目标的常见行为）。故默认走**编码值直接线性组合**，`--blend=lin` 仅作对照。

2. **缺口判据**：不能再用"固定走廊半径 + α<常数"，因为横截面本来就是 `u_core→1` 软边淡出。改为：
   - 走廊半径 = 标称半宽。
   - 每像素计算 `expect = 1 − smoothstep(u_core, 1.0, dist / half)`。
   - 若 `α < 0.5·expect`，则累计缺失覆盖量；`gap_px = 缺失量 / 标称宽`。
   - 走廊端点（平切端造成的越界）会被 `atCap` 识别并排除，不是缺陷。

3. **汇流三宽分解** `W_tributary / W_junction / W_trunk`：
   - `gap_px = 0` 硬要求已满足。
   - `W_junction` 的读数会比两侧大：这不是鼓包，而是**两条带在汇流格交叉**的几何必然。实测汇流角 63°，交叉预期宽度 ≈ 8.01 px，实测 W_junction ≈ 6.74 px，比值在 1.17–1.20 之间 ⇒ 与"两条带正常交叉"一致，没有异常鼓包/缩窄。

4. **depthOrderingError**：只在两条带都实际覆盖且均为实心（α>0.5）的像素上判归属。灵敏度对照——把 `--bias=0.0001` 强制拉平后，错误率从 0–33% 跳到 **100% 支流胜** ⇒ 指标确实在量 bias 分层机制本身，不是噪声。

5. **弯道护栏复测**：直接复算 `RiverPresentationSpline` 的 `MaxDeviationRatio`。`devRatio` 实测 0.085 ≤ 0.15；原生锚点转角 70.4°，窗口样条最大转角 29.4°（明显柔化但没有"被拽走"）。

### ★★诊断命名语义：`depthOrderingError` → `depthOrderingMismatch`（2026-10-05 已改名）

> **Mismatch ≠ topology / rendering failure。**

| 名称 | 定义 |
|---|---|
| **本工具测的** `depthOrderingMismatch` | 在"两条带都实心覆盖（α>0.5）"的重叠区内，**支流色占主导**的像素比例 |
| **严格意义的 failure** | **"本应前置的 surface 被后置 surface 覆盖"**的像素比例——本工具**不直接测**这个量（交叉区里两层本来就 alpha 混合，边界像素归属是连续过渡，不是二值事件） |

Mismatch 高 ≠ 渲染失败，它包含两类：① 真 depth inversion；② **预期的**像素归属混合
（两条半透明带叠在一起时，"谁占主导"本就是程度问题）。

⇒ **唯一可靠的判别方式是灵敏度对照**：`--bias=0.0001` 把两层 bias 拉平后，
指标应从 X% 跳到 ~100%，才说明它在量 bias 分层机制。
实测：生产（支流 1e-4 / 干流 2e-4）**0–33%** → 拉平后 **100%** ⇒ 当前 `2e-4 > 1e-4` 的设计有效。
