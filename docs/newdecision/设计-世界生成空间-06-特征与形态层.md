# 世界生成空间 · 06 · Field + Feature + Morphology（架构决策，已落地骨架）

> 定位：承接用户 2026-10-03 架构决策——**"区域"不该是所有地形生成的统一空间单位**。
> 大陆/山脉/丘陵/盆地/峡谷/火山天然不同尺度、不同形状、不同边界；强行依附 Region
> 就是"先切块再往块里塞地形"。正确分层：**Field（原因）→ Feature（对象）→ Morphology
> （生长规则）→ Terrain Field（高度贡献）**。
> 上篇：[04-山脉骨架](设计-世界生成空间-04-山脉骨架.md)（v3.2 已是事实上的第一个 Feature+Morphology）。

## 0 一句话判断（决策 §十）

> **Region/Field 回答"这里发生什么事情比较容易"；Feature 回答"具体形成的东西长什么样"。**
> 两种信息彻底分开；不存在万能地形区域公式（§十一：山脉用沿线坐标 s+d、盆地用局部
> 2D、火山用径向 r/θ、河流用流线 s+d、海岸用离岸距离 d）。

## 1 落地代码映射

| 层 | 代码 | 职责 |
|---|---|---|
| **Field** | `TectonicField`（新） | 陆块主轴（PCA）、**构造强度连续场**（区域类型 → 基值：Mountain 1.0 / Highland .75 / Rift .7 / Plateau .6 / Plain .35 / Basin .3 / Coastal .2，Shepard 帽插值，跨海连续）、锚点池 + 强度加权选址、方向扰动噪声。**只回答"哪里容易"，不负责任何形状** |
| **Feature** | `TerrainFeature` 基类（新）：Anchor / OrientationRad / **Intensity（场读数）** / **Scale3（纵/横/垂三元组）** / 预筛帽；`MountainSystemFeature : TerrainFeature`（第一个完整 Feature，骨架 Generate 时注册，Scale = 脊长/2σ/脊高） | 离散地质对象的公共身份 |
| **Morphology** | `MountainSkeleton`（重构定位）：中心线随机游走 + 轴向高度曲线 + 支脉树 + 海洋表达式——**MountainRange 的生长规则**；实现 `IHeightContribution`（`Sample(dir)` 统一口） | "这个东西具体长成什么样" |
| 合成 | `HeightComposer`（不变） | 只认 `IHeightContribution`——特征内部形态对合成器不可见 |

## 2 这次重构改变了什么

1. **环境场上收**：PCA/方向噪声/锚点池从 MountainSkeleton 肚子里抽出为 `TectonicField`——未来盆地/火山/峡谷的 Feature **直接读同一构造场**（`IntensityAt` + 各自阈值），不碰总架构。
2. **选址语义升级**：山脉锚点从"池内均匀随机"改为**强度加权**——山真的长在"构造强度高"的地方（Field 的"原因"语义第一次闭环）。
3. **身份与形态分离**：`MountainSystemFeature` 只携带身份（锚/走向/强度/尺度），形态数据（点列/剖面/支脉）留在 Morphology——将来序列化/调试/UI 逐层可查。
4. **GeologicalRegions 降级为轻量背景**（决策 §六 TectonicDomain 方向）：仍产出区域类型与基础高度，但不再约束 Feature 形状——山脉本来就跨多个区域（v3 事实），现在架构上也承认了。

## 3.5 #13 Final 空间索引 v1（2026-10-03，"Final World 空间查询基础设施"）

按用户定位落地：**索引 Final World 的事实，不是生成器内部状态**；v1 刻意窄——
只做 nearest/distance/within（Point → nearest Landmass/Region/River/Mountain/Volcano）。

**实现**（`FinalSpatialIndex`）：
- 面状事实（陆块/区域/河流）= **多源 BFS 距离场**：预计算 O(n) 一次（label+dist 双场），
  逐格表查询 O(1)——批量查询天然廉价（表即预计算的批量结果）；陆块/区域溢出到海
  （海上问"最近的陆/区域"即得），河流 label = 源格索引（返回最近河流格）。
- 点状事实（山系/火山锚点）= O(K) 暴力（K ~10-30 暴力即最优；KD-tree 留 K 上千）。
- 距离口径 = H3 图距（跳数），与 FinalDistToCoast/DistToLand 同口径；任意方向查询经
  dir → H3 格 → 表（格粒度精度）。
- **输入纯数据化**：山/火山锚点与河流格列表作为构造/Generate 参数传入——本类对
  Placement 投影器/Feature 生成器/TectonicField/SurfaceResolver/RiverNetwork 零引用
  （ArchitectureContractTests.SpatialIndex_OnlyDependsOnFinalWorld 反射钉死，
  forbidden 9 类）。

**验收四层**：① 语义（索引=暴力遍历对照：陆块 argmin+跳数一致、最近山锚一致）
② API（nearest/distance/within 行为：陆格自身 0 跳、海格最近陆、河流格 0 距、
无河流世界 −1）③ 性能（预计算 O(n) 一次 + O(1)/O(K) 查询——批量查询=表查询）
④ 架构（反射契约）。+5 例于 681 总盘。

接线：WorldGenPlanet.Generate 尾部（山锚/火山锚/RiverMask 提取 → 索引构建）。
River v1 基准图保留（不调阈值）。

## 3.6 #13 v1 正式冻结 + River 2 三段契约（2026-10-03，用户拍板）

用户结论：**#13 v1 可以正式冻结**。冻结理由不是"做完了"，而是**设计边界判断正确**——
面状事实走多源 BFS 距离场（预计算 O(n)、查询 O(1)，距离场本身就是批量查询缓存），
点状事实走 O(K) 暴力（K~10-30）**优于**为"空间索引"三个字上 KD-tree/R-tree。

### 冻结面（此后不动，除非用户解冻）

| 冻结项 | 内容 |
|---|---|
| 面状事实 | 陆块/区域/河流 = 多源 BFS `label+dist` 双场，一次预计算、逐格 O(1) |
| 点状事实 | 山系/火山锚点 = O(K) 暴力（KD-tree 留到 K 上千，届时再解冻讨论） |
| 距离口径 | H3 图距（跳数），与 FinalDistToCoast/DistToLand 同口径；任意方向经 dir→格→表 |
| API 面 | 只暴露 nearest / distance / within（不新增 join/范围聚合/kNN-topN） |
| label 语义 | 面状 = 最近源（陆块号/区域号/**源格索引**）；点状 = 锚点向量 |
| 依赖面 | 只消费 Final World 事实数据；禁引用 Placement/Feature/TectonicField/SurfaceResolver/RiverNetwork |
| 区域距离 | `NearestRegionDistHops` **有意不暴露**（v1 冻结面）→ 区域只验身份不验距离 |

### ★永久验收原则（BFS label bug 的沉淀）

> **所有 nearest 查询必须同时验证"距离正确"与"对象身份（label）正确"。**

bug 本体：River BFS **结构完全正确、distance 也可完全正确**，但 `label = 0` 常量使
`NearestRiver` 恒返回格 0——"最近哪条河"的事实失效。修复后 `label = sourceCellIndex`，
`NearestRiver` 才同时具备 `distance → 最近` 与 `label → 是谁`。
**类别定性：算法结构正确、语义字段错误**——只测数值（distance/influence/count）的测试
抓不到这一类，必须引入身份断言。

钉子落点（SpatialIndexTests，四支事实全覆盖）：

| 事实 | 距离验 | 身份验 |
|---|---|---|
| 陆块 | `NearestLandmass_MatchesBruteForce`（暴力 argmin 跳数） | 同例 `NearestLandmassId` 对照 |
| 河流 | `NearestRiver_MatchesBruteForce_IdentityAndDistance`（新增） | 同例：label ∈ 河流真值集 **且** 该 label 自身处于最小跳数 |
| 山锚 | `NearestMountain_MatchesBruteForce`（distRad） | 同例 `anchor` 向量对照 |
| 区域 | v1 未暴露距离场 → 只验身份 | `NearestRegion_MatchesBruteForce_Identity`（新增）：label 区域处于真实最小图距 |

身份基准**独立**（河流格真值来自 `RiverNetwork` 输出，不从索引自身反推——否则退化成自证）。

## 3.8 2B 收口 + 2C 语义边界（2026-10-03，用户拍板：**先钉边界，再动实现**）

### 2B 架构收口：三层职责分开（不是"河线变连续了"）

| 层 | 代码 | 回答 |

### ★沉淀原则：原子事实优先于分类（孤立河案例）

孤立河（单格河）**同时是 Source 与 Outlet** 这一案例证明：`NodeKind` 不应承担"事实集合"职责。

- **原子事实**（独立可读、可同时成立）：`DownstreamRiver < 0` ⇒ 出口性；`UpstreamCount == 0` ⇒ 河源性。
- `NodeKind` = **表现性分类**（单一标签，优先级 出口 > 河源 > 汇流 > 干流/支流）。

⇒ **永久原则：先保存原子事实，再由分类做表现；分类不得覆盖事实。**
（分类标签怎么调，原子事实仍可查——本例正是靠"出口性"从 `DownstreamRiver` 直接读出，才敢让类型优先级压过河源。）

### 2C 核心原则

> **Lake / Basin 是 Flow Graph 的拓扑结果，不是第二套水体生成器。**

不要 `FinalHeight → LakeGenerator → 另外生成湖`；
而要 `FinalHeight → Flow Direction → Flow Graph → {Ocean Outlet | Closed Basin} → Basin → Lake`。

### 2C-A：Basin 拓扑（先 Basin，不 Lake）

**Basin 定义**：一组**最终没有流向海洋、而是终止于同一内流终点**的汇流单元。
先不要直接把闭合汇流区域叫 Lake——因为**内流盆地 ≠ 一定有湖**，两个概念从第一天就分开。

产出：`Ocean Basin` / `Endorheic Basin` / `Outlet` / `BasinId` / `BasinArea` / `Accumulation`。
**这一阶段甚至可以不画湖**——只回答"这个水最终去了哪里"。

### 坑：flow termination ≠ lake

当前 Flow Graph 已允许 `River → 内流洼地 → termination`，但**终止点不等于湖**：至少还缺一个
**水量/蓄水条件**。否则世界上每一个因离散网格、局部高程结构产生的内流终点都会变成湖。

### 2C-B：Lake 判定（水量平衡）

再回答"这个内流 Basin 是否形成稳定水体"，此时才引入：降水输入 / 汇流量 / 蒸发·损失（若模型已有）/
Basin 容量·最低溢出高程 / 水面高程。产出：

```

```

（同族 bug 已抓到两次：label 没接、cellWeight 没接。）

## 3.10 River 2C-B 落地（2026-10-03，LakeState——水量平衡，不改拓扑）

**代码**：`scripts/noise_world/worldgen/LakeState.cs`（接线 `WorldGenPlanet.Lakes`）。
只解决一件事：**内流流域是否形成湖 + 湖的水量状态**。

```
降水/汇流输入 ──> 水量平衡 ──> SurfaceElevation ──> Area / Volume / Overflow
（**不是** AccumMm ──> Volume）
```

### ★AccumMm ≠ Volume（本轮最重要的一条）

`BasinGraph.AccumMm` 是**出口格累计径流量**（流域汇流事实，单位 mm）；
`Lake.VolumeKm3` 是**水量平衡后的状态**（由水面高程 × 淹没格体积算出，单位 km³）。
Lake 的来水量**自己按流域降水求和**，不取 `AccumMm`——否则将来加入蒸发/渗漏/蓄水容量/
季节变化时，Lake 会被迫重新解释 River/Basin 的统计量。
测试同时钉住：来水量与 `AccumMm` **数值一致**（同一份水的两种算法），但 Volume 由几何算出
（`Σ(水面 − 格底) × 格面积`）——**一致的是输入，不是定义**。

**v1 退化解**：无蒸发/渗漏模型 ⇒ 零损失 ⇒ 未溢出的湖把来水全部蓄住
（Volume 数值上 = 输入水量）；来水超过容量 ⇒ 水面**收敛到最低溢出高程**并产生溢出出口。
这是"零损失"的物理推论，不是定义——将来引入损失项后，Volume 自然不再等于输入。

### 字段

| 字段 | 语义 |
|---|---|
| `BasinIdOf` / `LakeOfBasin` | Lake 与 Basin **一一绑定**（不允许脱离 Basin 的水体） |
| `SurfaceElevationM` | 水面高程（≥ 流域最低点，≤ 最低溢出高程；溢出 ⇒ = rim） |
| `AreaKm2` / `VolumeKm3` | 淹没格数 × 格面积 / `Σ(水面−格底)×格面积`（**Volume > 0 才算湖**） |
| `SpillElevationM` | 最低有效溢出高程 = 流域外相邻格的最低高程 |
| `OutletCell` | **溢出事实独立**：未溢出 = −1；只有水位达到 rim 才存在出口 |

### 验收 9 例（`LakeStateTests`）

只有 Endorheic 成湖（Ocean 永远不生成 Lake）/ **内流 ≠ 必然有湖**（湖数 ≤ 内流流域数）/
Lake 与 Basin 一一绑定 / 水面不违反地形（≥ 底、≤ rim、溢出 ⇒ = rim）/ 溢出是独立事实
（且 Lake 溢出点 ≠ 流域终止陆格，两套事实不混）/ Volume·Area 几何一致 + Volume > 0 /
来水量与汇流事实一致但 Volume 不由 AccumMm 定义 / **零损失退化解**（1mm ⇒ 全蓄存；
巨量 ⇒ 收敛到 rim 并溢出）/ **架构退化**（FlowDirection·FlowAccum·RunoffAccum·IsRiver·
RiverGraph·BasinGraph 全部逐格不变）/ 确定性。

### 契约

`LakeState` 并入两条水文契约（不依赖 SpatialIndex/Placement/Feature；不引用旧气候线）；
`BasinGraph_DoesNotDependOnLake` **从此真正生效**——`LakeState` 名字以 Lake 开头，
BasinGraph 一旦引用即红 ⇒ 保证 Lake 与 BasinGraph **并列**接入 WaterSystem。

- basin40（9 格）水面 461.2 m、basin64（20 格）291.3 m（均溢出）、basin89（9 格）399.8 m（未溢出）。
- **basin26：内流但零容量**——洼地底 = 溢出高程 = 30 m（`MinLand` 钳制造成的平底退化洼地）
  ⇒ **不成湖**。这正是"内流盆地 ≠ 一定有湖"的实证，也说明 `termination ≠ lake` 不是口号。
- 登记：res1 格面积 607,221 km² ⇒ 单格即 60 万 km² 的湖（尺度失真），**res4（1,770 km²）才有判读意义**；
  v1 未建模蒸发/渗漏/季节变化（零损失），属 2C-B 的后续增强点。

## 3.11 River 2C-C 落地（2026-10-03，WaterTopology——水体之间的连接）

**代码**：`scripts/noise_world/worldgen/WaterTopology.cs`（接线 `WorldGenPlanet.WaterSystem`）。
它回答"**水从哪里来、经过什么水体、最终去哪里**"，**不重新定义河流或湖泊本身**。

### ★永久原则：四个概念不互相吞并

| 层 | 回答 | 不回答 |
|---|---|---|
| `RiverGraph` | 河流**内部**拓扑（source/汇流/outlet/干支流） | 水体的连接关系 |
| `BasinGraph` | 流域归属与终止（Ocean/Endorheic + BasinId） | 有没有湖 |
| `LakeState` | 湖泊状态（水量平衡后的水面/面积/蓄量/溢出） | 湖之后的水去哪 |
| `WaterTopology` | **上述水体之间的连接**（River→Lake→River→…→Ocean） | 不重算任何一层的事实 |

**Lake 的 `OutletCell` 不直接变成 RiverGraph 的节点**：
`LakeState ──OutletCell──> WaterTopology ──> 出口之后的 downstream water body`。
因此未来 `River → Lake A → River → Lake B → River → Ocean` **完全不需要让 RiverGraph 知道 Lake 的存在**。

### 数据形状（v1，克制）

- 节点：`River`（一个河系，以出口格为身份）/ `Lake`（湖下标）/ `Ocean`（单一海洋水体）/ `EndorheicSink`（按流域）。
- 边：每个节点**最多一条出边** `Next`，连接发生的格记 `ViaCell`（可追溯）。
- `TraceFrom(node)` / `TraceFromRiverSource(cell)`：得到 `River → … → 终端水体` 的完整路径。
- `lakes` 允许为 `null`（无湖泊层）⇒ **退化**为既有 River → Ocean / Endorheic 终止结果。

### 验收 7 例（`WaterTopologyTests`）

① RiverGraph 完全不变（`DownstreamRiver/UpstreamCount/NodeKind/Sources/Outlets` + **Geometry 线与点**逐项一致）
② LakeState 完全不变（只读取，不重新计算湖泊）
③ 跨水体连接可追溯（从任意河源出发 ⇒ 首节点是 River、末节点是终端水体、路径无重复）
④ **Lake → River 必须是真实下游河流**：连接点在溢出格的 `Downstream` 路径上（不是"恰好邻接"），
且出口河流属于**另一个**流域（水确实流出了本流域）
⑤ 不允许环（尤其 `Lake A → River B → Lake A`）：每个节点沿出边走必须终止且不重复
⑥ **退化**：无湖泊层 ⇒ 每条河的终端与 `BasinGraph` 终止事实逐项一致；且**有湖流域之外**的河系终点与退化情形完全相同
⑦ 确定性逐位同

契约：`WaterTopology` 并入两条水文契约（不依赖 SpatialIndex/Placement/Feature；不引用旧气候线）。

### res1 实测与登记

5 个节点（**1 河系 / 3 湖 / 1 海洋**），边：`River→Lake` ×1、`Lake→Ocean` ×2、`Lake→END` ×1（封闭湖）——
即"唯一的河注入一个湖，其中两个湖溢出入海、一个封闭"，无环。
登记：res1 在降水阈值下只有 1 个河系（统计意义要等 res4）；**本版不做**湿地/沼泽/洪泛平原/季节水位。

## 3.12 空间尺度 / 单位层 D-10（2026-10-04，res 与物理量解耦）

用户拍板的核心规则：**res 只是采样/离散化精度，不应该改变任何物理参数的意义。**
这不是"某个算法算错了"，而是**整个模拟系统缺少一个统一的"空间尺度/单位层"**——
最直观的暴露就是 2C-B 发现的"res1 单格就是 60 万 km² 的湖"。
处置：**作为收口阶段的基础设施工作，不重新设计 WaterSystem**（§07 §7 完整记录）。

### ★三类参数（此后见到任何参数先问它属于哪一类）

| 类 | 含义 | 典型 | 正确单位 |
|---|---|---|---|
| **A 拓扑尺度** | 图上的离散结构 | BFS 距离 / H3 hop / 邻居数 / 图深度 / 成员格数 | `cell` / `hop`（**与 res 强相关，永不跨 res 比较**） |
| **B 几何尺度** | 真实世界的空间大小 | 面积 / 距离 / 山脉宽度 / 河长 / 湖面 | `km` / `km²` / `km³` |
| **C 物理尺度** | 真实世界的物理过程 | 降水 / 蒸发 / 径流 / 水量 / 侵蚀 | `mm` / `mm·a⁻¹` / `km³` |

> ★**res 只决定"一个格子有多大"；物理参数决定"现实世界有多大"；两者不得混在一起。**
>
> 拓扑问题 → hops；物理问题 → km / km²。**这个边界非常重要。**

### 建层前先测（不靠推断）

探针（`PerfBench --probe`）实测：同一世界里"一格多大"曾有**三套口径**——
H3 平均面积表（`LakeState`，硬编码 9 档）、内联的 `4πR²/n`（3 处）、人文层自己的 `4πR²/N`。
res1 下前两者差 0.24%：**看似小，但它意味着两套面积真相源并存。**

> ★**纠正的一次错误推断**：曾怀疑 H3 `res` 编号偏移导致面积放大 7 倍，**实测不成立**。
> **教训：口径问题必须实测，不能靠"官方文档对照表"推断**（本项目 `res` 编号与 H3
> 文档确实错位一档，但错位方向恰好让数值仍自洽，极易误判）。

### `SpatialScale`（薄层，四个口径各有分工，不合并）

| 成员 | 口径 | 用途 |
|---|---|---|
| `CellAreaKm2` | **等积** `4πR²/n` | **默认**；所有面积 ⇄ 格数换算。选它因为 `Σ = 4πR²` **严格守恒** |
| `ExactCellAreaKm2(cell)` | **H3 精确** | 最终判读 / 渲染 / 精度敏感（O(n) native） |
| `DistanceKm(a,b)` | **真实大圆** | 一切"物理距离"；已验证与 `H3.CellToLatLng` 口径一致（差 <1 m） |
| `HopDistanceKm` | **有偏近似** | 仅量级表述 / UI；实测偏差 18.7~28.7%，**不得用于模拟** |

`AreaConserving` 是自检口：`CellAreaKm2 × CellCount == 4πR²` 恒等式。

> ★**实施中抓到自己的 bug**：`DistanceKm` 初版把已算好的弧度又乘一次 `d2r`
> ⇒ 距离缩小 57 倍。**静态看公式完全正常**，是探针的"逐邻居实测"照出来的
> （res1 邻格距 88 km vs 期望 837 km）。
> ⇒ **新基础设施层必须配"活体对照"**：不是"公式看起来对"，而是"与独立实现逐点对齐"。

### 面积阈值从"格数"变"面积"（`40 格` 跨 res 差 34 倍）

| res | 格数 | 每格 | `40 格` = 流域面积 |
|---|---|---|---|
| 1 | 842 | 605,777 km² | **2,431 万 km²** |
| 4 | 288,122 | 1,770 km² | **7.08 万 km²** |

新的物理口径 `RiverThresholdAreaKm2 = 70,800 km²`（黄河量级，res4 下 ≈ 40 格平滑对接）。
新增 `BasinGraph.AreaKm2` / `RiverNetwork.FlowAccumKm2`（= 汇水面积 catchment area）/
`RunoffAccumKm3`；**格数字段全部保留**（它们是拓扑量，收敛判据要用）。

**★退化解成立**：同一 res 下格数阈值 `T` 与等价面积阈值 `T×A` 判据**逐格完全一致**
⇒ 迁移零行为漂移。跨 res 时才显出"物理阈值才是尺度无关的那个"。

### 分辨率收敛（`ResolutionConvergenceTests` / `PerfBench --converge`）

**目标不是"每个格一模一样"，而是"提高 res ⇒ 宏观统计量趋于稳定"。**
实测（seed 42，物理阈值 70,800 km²）：

- ✅ **陆地占比收敛**：29.22 / 29.46 / 29.13 / 29.02 %（极差 0.44 pp）⇒ 证明单位层没引入漂移；
- ❌ **河流密度跨 100 倍**：占陆地格 100% → 81.8% → 12.9% → 0.98%；
- ⚠️ **过半流域是"单格流域"**：中位流域面积**精确等于**格面积（四档比值都是 1.000）⇒
  这是内流占比冲到 35% 的直接原因。

**根因（两个，独立）**：① **阈值在粗网格下失效**——res1 一格 605,777 km² ≫ 阈值
⇒ 整块陆地都是河；② **噪声相关长度 vs 采样密度不匹配**——三档噪声波长
5000/600/90 km **本身正确**，但 res4 每格 26 km（90 km 噪声仅 3.5 格）⇒ 攒不到汇流。
⇒ **水文模型的有效工作尺度集中在 res2 附近**，但**项目生产分辨率 = res4 冻结**。
   ⚠️ 该差异被认定为**水文模型的尺度适配缺陷（D-11）**，
   **不得通过降低生产分辨率规避**（用户 2026-10-04 二次拍板，§07 §5.5）。
   否则会滑向"某模块在 res4 不工作 → 换 res3 → 换 res2"的架构倒退。
   ⇒ 正确方向：让水文适配 res4（采样密度 / 空间相关长度），不是改阈值或降档。
   全库统一表述：✅ 生产 res4；✅ 水文有效工作尺度 ~res2；⛔ 生产档 res2 / 特征分辨率。

**处置：不调参。** 把噪声/阈值调到"看起来收敛"是**为指标而调参**。
两条缺陷以**特征测试**钉现状（注释标明"修好后本测试会红并提醒改写为收敛断言"）。
只有出现真实消费者（可通航的河、灌溉水量）才重新评估阈值——那时"多大算一条河"才有答案。
