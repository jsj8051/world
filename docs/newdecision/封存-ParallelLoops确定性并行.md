## 2 ★核心知识一：确定性并行的**判据**（什么能并行、什么不能）

原文：

> 只用于**地图型**核函数：每个输出元素恰好被一个迭代写一次、迭代间无读写耦合
> （Laplacian、逐格物理量缓存、驱动速度场、降水/温度场这类）。
> 逐元素浮点算式与串行版逐位一致，因此同入参结果与串行版逐位相同 ——
> 模拟的"同 seed 逐位可复现"纪律不受并行影响。

> ★**约约型**循环（Σ、float 累加）**不许走这里**：求和顺序随调度变化
> 会破坏逐位一致（确需并行的整型计数用线程局部 + 整数合并 —— **整数加法精确且可结合**）。

### 三类循环的并行判据

| 核函数形态 | 能否并行 | 原因 |
|---|---|---|
| **地图型**（写只落 `i` 自己的输出位） | ✅ 可 | 无跨迭代耦合，逐位同串行 |
| **约简型·浮点**（Σ、float 累加） | ❌ **禁止** | 求和顺序随调度变化 ⇒ 破坏逐位可复现 |
| **约简型·整型/精确可结合**（计数、min/max） | ⚠️ 需走 `ForWithLocal` | 整数加法精确且可结合 ⇒ 合并结果与调度无关 |

★**这是本工具最核心的知识**：确定性并行的门槛**不在"能不能并行"，
而在"归约是否精确可结合"**。

## 3 ★★核心知识二：那个竞态（封存的最高价值）

`ForWithLocal` 的注释（`:37-40`）原文：

> `combine` 按 worker 各调一次、**锁内串行执行** —— 合并结果只由合并运算的
> 可结合性决定，与调度无关（⚠️ 浮点 Σ 不可结合，仍不许走本口；
> **无锁 combine 会被 `Parallel.For` 在多 worker 上并发调用，连 max 都可能丢更新
> —— 本竞态实测抓到过**）。

### 为什么这条值得单独记

`Parallel.For` 的 `localFinally` 参数是**按 worker 调用**的，
**不是全局一次**。若在 `localFinally` 里直接做 `globalMax = Math.Max(globalMax, local)`
而不加锁：

- 多个 worker **并发**读 `globalMax`、算出各自的候选、写回
- 经典 read-modify-write 竞态 ⇒ **较小的值可能覆盖较大的值**（丢更新）
- ★**连 `max` 这种"看起来天然可结合"的运算都会丢** ——
  因为问题不在结合性，而在**复合赋值不是原子的**

⇒ **正确做法**（代码里的写法）：

```csharp
object combineGate = new();      // 私有锁对象，不复用 this（避免外部干扰）
Parallel.For(0, count, localInit, body,
    local => { lock (combineGate) combine(local); });
```

两个细节：
- ★**锁对象是私有的 `new object()`**，不复用 `this` —— 避免与外部代码互相干扰
- ★**`combine` 在锁内** ⇒ 每个 worker 的局部结果串行合并

### 推论

> ★**"运算可结合"不等于"合并安全"。**
> 可结合性保证的是**结果只由运算决定**；
> 但**结果的写入**仍需原子性 —— 复合赋值（`x = f(x, y)`）**不是**原子的。

## 4 三个 API 与各自的设计意图

| API | 用途 | 关键设计 |
|---|---|---|
| `For(count, body)` | 地图型并行 for | 直接 `Parallel.For`；小场/单核直跑串行 |
| `ForWithLocal<TLocal>(...)` | 带线程局部约简 | **仅限精确可结合的合并**（整数计数、min/max）；`combine` 锁内串行 |
| `ForFixed(count, workers, body)` | **固定分块**（设计 11-2 §2.4） | 块的**数量与区间只由入参决定**，不依赖调度器动态分区 |

### `ForFixed` 的设计意图（值得单独记）

原文：

> **固定分块**地图型并行 for —— 「跨运行确定性」在框架层的**兜底**。
> 与 `For` 的区别：块的**数量与区间只由入参决定**（块数 = workers，
> 块 b = `[b·count/B, (b+1)·count/B)`），**不依赖运行时调度器的动态分区**
> ⇒ 即使将来有人误把归约型循环接进来，跨运行/跨线程数的划分也恒定可复现。

另一个细节：

> worker 数由**调用方专用字段**传入，**不读全局 `WorkerCount`**，
> 避免外溢到其他共用调用方（设计 11-2 §5 的 ★修正纪律）。

★即"**每个调用方自己声明 worker 数**"，避免一个调用方改 worker 数影响其他人。

## 5 门槛：为什么小场不该并行

原文：

> 格数低于 `MinCellsForParallel`（32 768 = 1<<15）或单核时直跑串行 ——
> 并行调度的**固定开销**（分区 + 线程池往返 ~几十 µs）在小场上反而变慢。
> **res3（41 162 格）起并行。**

| 档位 | 格数 | 是否并行 |
|---|---|---|
| res1 | 842 | ❌ 串行 |
| res2 | 5,882 | ❌ 串行 |
| res3 | 41,162 | ✅ 起并行 |
| res4 | 288,122 | ✅ |

★**这张表今天仍然有效**（res3=41,162 > 32,768 门槛），可作将来需要时的判据。

## 6 现状：S-6 的真实解法（供对照）

**S-6 原症状**（审查报告 `:190-202`）：地形/地质生成全在主线程同步执行，首帧冻结数十秒。
res4 下`MountainSkeleton.InfluenceAt` =逐格 × 帽内全脊 × 脊上全点 = **2e8–8e8 次 `MathF.Acos`**。

**实际解法 = 算法剪枝，不是并行**（决策 04 §24）：

| 手段 | 效果 |
|---|---|
| 逐脊**角帽预筛**（`dir.Dot(Center) < cos(CapRadius)` 即 `continue`） | 把大部分 (dir, 脊) 对直接排除 |
| **3σ 截断**（`exp(−9)≈1e-4`） | 帽内但影响可忽略的也排除 |
| `cs:209` `_rugged.Sample(dir)` 放大 5–20× | 已修（只依赖 `dir`，且在截断之后） |
| `NoiseTerrain.SampleRawFields`（另 5.3e7 次哈希） | 随 B 线清退整体删除 |

**复测（2026-10-05）**：主入口 headless res4 = **8,368 / 8,349 ms**；
PerfBench res4 全链 **4,224 ms**，`MountainSkeleton` **347 ms**。

★**关键事实**：世界生成链**至今仍是零并行**（全库 8 处真 `Parallel.For`
都在 `GoldbergBuilder` / `ChunkMeshBuilder` 网格构建，不在生成链）
⇒ **症状是靠"少算"解决的**。

## 7 将来若需要确定性并行，按什么起步

⚠️ **不要复活本类**。它的问题是"从未验证"（无任何使用记录 ⇒ 无回归测试保护）。
若将来真的需要（例如生成链某个阶段实测超预算），应当：

1. **先证明瓶颈仍在**（当前 res4 全链 4.2s，热点是 `H3LandSeaProjector` 1.65s 与
   `Ball` 构造 1.29s，**都不是"逐格浮点地图型循环"** ⇒ 本工具的适用范围未必对得上）
2. **先写退化解测试**（单worker / 小 `count` 时必须与串行逐位同）
3. **约简型一律走 `ForWithLocal` + 锁内 combine**（§3的竞态必须重演防护）
4. **worker 数由调用方专用字段传入**（不读全局）
5. ★**先问"能不能少算"** —— S-6 的经验表明**算法剪枝往往比并行收益更大、风险更低**
   （剪枝是确定性的，引入线程则要额外守逐位可复现）
