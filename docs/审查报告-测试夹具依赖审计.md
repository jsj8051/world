## 1 审计方法（三层，与清退判定三层同源）

| 层 | 问题 | 手段 |
|---|---|---|
| ① | 测试引用了哪些生产类型？ | 反射式扫 `new <生产类型>` + `typeof` + 断言上下文 |
| ② | 是什么用途？ | 被测对象本身 / 造场 fixture / helper-builder / 诊断工具 |
| ③ | 该生产抽象是否"只是方便造数据"？ | 统计**生产侧**消费者数（排除测试） |

★**第①层的方法学教训（本次实测）**：只搜 `new Xxx()` 会**大量误报**。
本次初扫得出"50 个C 档候选"，逐个核实后**只剩 3 个**。误报来源有三类：

| 误报来源 | 例子 | 真实消费方式 |
|---|---|---|
| **`.tscn` 场景挂载** | `WorldGenPlanet` / `WorldGenManager` / `CellInfoCard` / `MapDock` | Godot 场景挂载（运行时依赖） |
| **静态方法调用** | `SeedDerivation`（8 个生产文件引用）/ `LogService`（20）/ `UserPaths`（6） | `Type.Method()`，无 `new` |
| **基类 / 接口 / 被继承** | `SphericalField` / `ITerrainField` / `TerrainFeature` / `MapMode` | 类型声明位置 |

⇒ **审计"零引用"必须同时扫 `.cs` + `.tscn` + 静态调用 + 继承链**，
否则会把 50 个活类型误判成死代码。这与 `.cs + .tscn + 资产引用边`是同一条方法学。

## 2 ★核心架构规则（建议永久写进 constitution）

> **测试可以依赖生产抽象来验证生产语义，
> 但不应仅因"测试造数据方便"而成为某生产抽象的唯一消费者。**

推论（两条禁令）：
- ❌ 不要为了"删除成立"而修改**被测组件的生产设计**（那是拿被测对象迁就测试）
- ❌ 不要为了"测试方便"把**本可清退的抽象留在生产代码**（这正是"假活跃代码"的成因）

## 5 ★★最重要的建议：给"悬空建议"加执行机制

（★本节结论已按 §3 的自我修正收敛：问题不是"判据与执行普遍脱钩"，
而是"**没有顺带被清退覆盖的死代码建议会永久悬空**"。）

本次审计暴露的真实问题不是 C 档，而是**悬空建议无跟踪**：

```
审查报告写下"直接删除，零风险"（2026-10-03）
        ↓
清单列了，没人执行
        ↓
2 个月后（2026-10-05）仍在生产树里
        ↓
★ 判据本身有效，但没有任何机制保证它被执行
```

⇒ **建议机制（择一或叠加）**：
1. **契约测试化**：把"应删"变成可执行断言
   （例：`FrameworkCompositionLayer_IsGone` / `LegacyNoiseWorldLine_IsGone`
   已经这么做了——**这也是为什么 B 线与组合层能真正删掉**）
2. **建议台账**：报告里每条"建议删除"给一个编号 +状态列
   （`待执行` / `已执行(commit)` / `已否决(理由)`），未闭环不许结项
3. **pre-commit 钩子**：对已知死代码清单做存在性检查（最轻量）

★**已有正面样本**：本轮 B 线与组合层清退之所以能真正落地，
靠的正是**契约测试把判据变成可执行断言**
（`LegacyWorldGenerationChain_IsGone` / `LegacyNoiseWorldLine_IsGone` /
`FrameworkCompositionLayer_IsGone`）。
`SphereLines` / `ParallelLoops` / `MathUtils` 缺的正是这一步——
**它们从未被写成断言，于是永远不会被自动发现。**
