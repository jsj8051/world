## A-1 ｜`WorldGenPlanet` 同时在干"生成"与"视图装配"

**症状**（[WorldGenPlanet.cs](../scripts/Scene/WorldGen/Composition/WorldGenPlanet.cs)）
一个类里混了三件事：
① 生成世界（`Regenerate()` → `Sim.Run`）；
② **装配并重烘视图**（`new BallView(...)` / `BuildChunks()` / `SetElevationSource()` / `RefreshColors()`）；
③ 持有河线叠加（`new RiverLineOverlay` / `Build` / `UpdateCameraScale`）。

按"管理器持有、组件干活"的分法，②③ 本该是 `BallView` 自己的入口（或一个 `WorldView` 节点），
星球只该"生成 + 把产物交给视图"。

**为什么暂时不动**
- 收益只是"分层更纯"，**眼前没有真实缺陷**：现在能跑、读数与基线一致；
  ⚠️ 但"重烘不变量"目前只由两个类之间的隐式契约维持（见下方"补充"①）⇒ 这是**潜伏风险**，不是零风险；
- 代价不小：`BallView` 的构造与重烘契约里含 LOD/剔除/切块的不变量（`BuildChunks` 与
  `SetElevationSource` 必须成对、重烘不得重建几何），拆出去要重新钉这些不变量；
- 判据 ①（防膨胀）：**先有真实消费者**——等第二个世界视图（或视图要能被替换/并存）出现时再拆。
  ★2026-10-11 更新：**装配那半已按用户拍板先拆了**（理由不是"等到了第二视图"，而是
  "先让三个管理器平级"这一结构目标本身）；**接口接线那半仍按判据 ① 挂着**，见"拆分结果"。

**修法（供将来）**
把 ②③ 抽成 `WorldView : Node3D`：构造拿 `WorldGenSimulation`，暴露
`Attach(sim)` / `Rebake()` / `SetCamera(cam)`；`WorldGenPlanet` 只保留 `Sim` + `Initialize`，
`WorldManager` 改为持有 `Planet` 与 `View` 两个子节点。

**⚠️ 补录（2026-10-11）：原修法只覆盖了症状 ②③ 两件事，范围不足。**

**补充（2026-10-11 补录·取证）**

起因：审查"点选链路"时提出的问题——"格子显示不是归 UI 侧吗？世界侧现在既装显示的东西，又装逻辑吗？"
取证结论：**"显示"不是一个单元，是两个；而混装落在哪，与原条目的表述不同**。

| 单元 | 文件 | 行数 | 现状 | 目标（`重整方案-按架构分层.md`） |
|---|---|---|---|---|
| 表现层（世界怎么画） | 17 | 1660 | `Scene/Render/` ✅ 已是独立目录 | `Render/` = `World.Render` |
| 界面层（面板与控件） | 2 | 270 | `Scene/Render/UI/` ✅ | `UI/` = `World.UI`（**与 Render 平级**，去掉 `Render.UI` 嵌套） |
| 装配层（场景怎么搭） | 5 | 434 | `Scene/WorldGen/` | `Scene/` = `World.Scene` |

① **表现层已是独立单元** ⇒ 本条的病根**不是**"世界侧装显示"，而是**装配粘在逻辑持有者身上**：
`WorldGenPlanet` 的 `Sim`（世界事实）与 `View`（世界画面）并列成两个属性，装配同时走两条线
—— 头注释第 13 行自称"引擎无关的那一半**全在** `WorldGenSimulation`"，而同一个类的
`Initialize` 里就在 `new BallView` / `AddChild` / `BuildChunks`。

② **原修法漏了两处**（跨类边界，拆 `WorldView` 时才暴露）：
- `WorldManager.PickAt` 里 `Picker.Highlight(cell.CellId)`（`WorldManager.cs:95`）＝ 管理器**替视图做事**，
  与"管理器持有、组件干活"不符 ⇒ 应由视图侧订阅选中结果，而不是管理器点名调它；
- `UIManager.Initialize(world, view, modes)` 握着 `BallView` 引用去驱动 `MapDockController`
  （`UIManager.cs:43`）⇒ 引擎侧 `Render`/`UI` 平级不互引（重整方案 R2）**要求这处改线**：
  界面拿到的应是"模式的索引/抽象"，不是视图本体。

③ **`Scene/WorldGen/` 的 5 个文件身份也不齐**：`WorldRoot` / `WorldManager` / `UIManager` / `ITickable`
是纯装配，`WorldGenPlanet` 跨装配与表现两项身份 ⇒ 同一个 namespace 里住着两种身份（同型于 A-2）。
拆分后 `WorldGenPlanet` 的身份应一分为二：`Sim` + 生成 ⇒ 装配；`View` + `_riverLines` ⇒ 表现。

**触发时机（修正·三档，逐档独立，不必一起做）**

- **T3｜等真实消费者（原判据 ①）**：出现第二个世界视图 / 视图需可替换时，才拆 `WorldView`；
  届时先把 ② 的两处接口改线，再动 `BuildChunks` / `SetElevationSource` 的成对不变量。

### A-1 收口：点选整体归渲染侧（2026-10-11 第二轮·用户拍板）

**用户判据（决定性的一句）**："实际是不是应该改成我说的"＋四点细化。核心问题被问对了：
拾取问的是**视图**（射线打 `BallView` 的球面）＋**相机**（客户端外围），选中结果的两个消费者
（高亮环 / 信息卡）也都不在世界侧 ⇒ **链路里没有一处需要世界管理器中转**。

| 项 | 收口前 | 收口后 |
|---|---|---|
| 点击信号 | `WorldManager._UnhandledInput` | **`RenderManager._UnhandledInput`** |
| 拾取 | 根管理器**注入** `WorldPicker` 给世界侧 | 渲染侧自建自用（视图就是它的） |
| 高亮 | 世界发 `CellHighlightChanged` → `WorldView` **订阅** | **就地** `View.SetHighlight(...)`（发起方即持有者） |
| 卡片 | UI 订阅 `WorldManager.CellPicked` | UI 订阅 **`RenderManager.CellPicked`** |
| `IHighlightPublisher` | 存在（选中在世界侧、高亮在表现侧 ⇒ 必须跨界） | **已删除**（选中与高亮同侧 ⇒ 接口没有存在理由） |
| `WorldManager` | 手势 + 拾取 + 两事件 + `SetCamera` 注入口 | **只剩** `Planet` + `Initialize` + 半径校验静态方法 |

★**数据来源一个字没变**（回答用户第 1 点"渲染侧的数据不也是从世界侧拿的吗"）：
`PickedCell` 12 个字段里，只有 `CellId`/`Index`（视图求交）与 `LatDeg`/`LngDeg`（H3 换算）不是世界事实，
其余 8 个全是 `Sim` 的（`Facts.Final.*` / `Terrain.DisplayElevation` / `Regions`）。
渲染侧早在上一轮就持 `sim` 引用（为 `Rebake()`）⇒ 改的是**装配工，不是数据源**。

★**相机 freshness 的取舍**（本轮自己发现自己踩的坑）：先把"每次点选前现取相机"写在 `PickAt` 里，
后改为**在 `Tick` 里刷**——那里本来就要取相机（LOD 用），**同一次取**顺手 `Picker.SetCamera(cam)`，
零额外开销，又不会把构造时那一台焊死（`OrbitalCamera.SetPlanetRadius` 支持换档 ⇒ 相机是可换的）。
**不缓存**（有意，已写进注释防"优化"）：Godot 节点释放是延迟的，"已排队释放但尚未删除"期间
`IsInstanceValid` 仍为真 ⇒ 缓存字段会拿死相机去射线，**点选静默失灵**。

**实测验收（2026-10-11 第二轮）**：构建 **0 警告 0 错误**；单测 **311/311**；
主场景 headless **exit 0 / 零 ERROR**（`[CULL-DIAG] chunks=122 visible=112 near=True camDist=3.40`）；
读数 **逐字同基线**；`H3SmokeDiag` exit 0。

### A-1 收口（2026-10-11 第三轮·用户拍板"彻底修复 A-1"）：`UI ↔ BallView` 解耦

**症状**（第二轮的"仍未做"）：坞的驱动器 `MapDockController` 只需"换取色函数 / 重烘颜色纹理"
两件事，却因此**持有整个 `BallView`** ⇒ 界面侧把球面渲染件的**生命周期、几何、LOD 面**全拖进了依赖；
`UIManager` 还要经 `render.View.BallView` 去掏它。

**修法（已实施）**：
- 新增表现层窄接口 **`IMapModeHost`**（`Scene/Render/`）：只有 `SetMode(MapMode)` / `RefreshColors()`；
- `RenderManager` 实现它（转发给视图）⇒ 它成为坞的"宿主"；
- `MapDockController` 构造收 `IMapModeHost` 而**不是 `BallView`**；`UIManager` 传 `render` 本体；
- **`BallView` 收为 `WorldView` 私有**：唯一还需要它的地方（建拾取器）改为视图自造——
  新增 `WorldView.CreatePicker(camera)`，理由：拾取本来就是"问视图命中哪一格"，
  视图最清楚怎么把自己的几何与事实源接上 ⇒ 不必把内部件借给装配层；
- `RenderManager.View` 一并收为私有（坞解耦后它没有外部消费者了）。

★**澄清耦合方向**（防误读）：UI 的耦合对象从 `WorldManager` 变成 `RenderManager`，
是**方向变对**了，**不是零耦合**。界面层仍然认识渲染管理器，这是设计（引擎侧三层的跨层协作）。

**实测验收（2026-10-11 第三轮）**：构建 **0 警告 0 错误**；单测 **311/311**；
主场景 headless **exit 0 / 零 ERROR**；读数 **逐字同基线**；`H3SmokeDiag` exit 0。
收口后实测接触面：`BallView` 的全仓非注释提及 = **0**（只剩两句"不认 BallView"的注释）。

**验尸结论：A-1 的原始症状已不存在。** 原条目列的三件事全部离开 `WorldGenPlanet`：
① 生成 → 留在它自己（本就该它干）／② 视图装配 → `RenderManager` + `WorldView`／
③ 河线持有 → `WorldView`；另有 ④ 相机 → `WorldRoot`、⑤ 点选 → `RenderManager`（均为同批收口）。
`WorldGenPlanet` 现 47 行，只剩 `Sim` + `Initialize`/`Regenerate`（原"两个尺度导出项"见下方同批收口）。

★**同日后收口**（用户："不需要 ResLevel 和 Radius 了，现在固定就好了"）：
`WorldGenPlanet` 上**两个 `[Export]` 已删**（它是本类最后的场景可填项，现一个都没有）：
· 分辨率 → `ProductionRes = 4` 编译期常量（原 `ResLevel` 实例字段只是它的影子）；
· 球半径 → 新常量 **`World.Constants.PlanetGeometry.ProductionRadius = 2.0f`**（**唯一的家**）。
  收口前半径有**三个副本各自填**（星球 `[Export]` / `Ball` 构造拷贝 / 相机 `[Export]`，
  场景里覆盖成 2.0），只有"相机 vs 星球"一处有运行期校验；现三方同源 ⇒
  `WorldRoot` 那条校验降级为"防人在场景里手改"的廉价守卫，
  `SpatialScaleTests.PlanetRadius_HasSingleSource_AndNoSceneOverrideNeeded` 钉死"同源真的发生了"。
  ⚠️ 实测细节：相机原缺省是 **6371**（已清退的 km 尺度世界的标定值），主场景把它覆盖成 2.0
  ⇒ **删掉场景覆盖是行为等价的**，已由 `camDist=3.40` 逐字不变验证。
  诊断要换档不再经本节点：自己 `new WorldGenSimulation(res, radius)`（`WorldGenReadoutDiag` 本就如此）。

**还剩两处接口接线（A-1 的"接线"那半 ⇒ 判据 ① 未到，挂起）**：
- ⬜ `UIManager` 仍持 `BallView` 引用（经 `MapDockController` 构造函数）⇒ 与"引擎侧 `Render`/`UI`

★**同批清掉**：`WorldManager` 的空 `Tick()` 已摘（逐帧活全归渲染管理器）⇒ 它不再是 `ITickable`，

**相机归属（2026-10-11 追加·用户指出"相机还挂在 WorldManager 下"）**：

  ⇒ **没有要管理器驱动的东西**，"为它建 ClientManager"属提前建设（同"不为单个类开目录"的判据）；
· WORLD 与 RENDER 两棵子树都要用它（拾取射线 / 逐帧剔除）⇒ **归中介者持有并分发**，
  与"`WorldParams` 不进场景树但归根管理器持有"同型；
· 副作用清理：`Camera.Cam.MakeCurrent()` 一行**删除**（`OrbitalCamera._Ready` 已设 `_camera.Current = true`，
  那行是多余的）；半径一致性校验从 `WorldManager._GetConfigurationWarnings` 移到 `WorldRoot`

### A-6 结案（2026-10-11 用户拍板"做下 A-6 吧"）

**落地**：新增 `scripts/Utils/Scene/PointerGesture.cs`（`World.Utils`，**非 Node 普通类**，与
`WorldPicker` / `MapDockController` 同型）——`Feed(InputEvent, out Vector2 at) → PointerIntent { None, Click, Drag }`，
阈值 `ClickSlopPx = 6f` **只定义一处**；两个消费者**各持一个实例**（各记自己的按下状态），判据共用。

| 消费者 | 改前 | 改后 |
|---|---|---|
| 点选（`RenderManager`） | `_pressArmed` / `_pressPos` ＋ 内联 `DistanceTo(...) <= 6f`（12 行状态机） | `if (_gesture.Feed(@event, out var at) == PointerIntent.Click) PickAt(at);` |
| 相机旋转（`OrbitalCamera`） | `motion && Input.IsMouseButtonPressed(Left)`（无阈值，靠全局按键状态） | `intent == Drag && @event is InputMouseMotion`（判据同源；不再读全局状态） |

主场景 headless exit 0 / 零 ERROR；读数逐字同基线。

★**两个设计取舍值得记**：
1. **`IsClick` 单独暴露成纯函数**（而不是埋在 `Feed` 里）：事件链需要引擎宿主才能造 ⇒
   单测只能钉住"真正会写错的那一行"（阈值 / 比较方向 / 距离口径），所以它必须可独立调用。
   **已做负向对照**：把 `<=` 改成 `<` ⇒ `IsClick_TrueWithinSlop_IncludingExactlyAtSlop` **当场报红**，
   恢复后复绿 ⇒ 边界那一格是真的被守住了（"正好 6px 点不中"是极难复现的偶发症状）。
2. **相机旋转的行为保持不变**：仍是"左键按下 + 有移动就转"（不引入"过阈值才开始转"，
   那会让前 6px 手感变空、且属另一个行为决定）。
   ⇒ 原条目"顺带修掉相机小毛病"这一半**改由新判据自然消除**：零位移的 `MouseMotion` 不再产生
   `Drag` 的旋转路径（`None` 或相对量为 0），滚轮与未按下的移动也不再被 `SetInputAsHandled()` 表态消费。
   ⚠️ 与旧实现的差异只有一处：判据从"读全局按键状态 `Input.IsMouseButtonPressed`"改为"读本次事件链"
   ⇒ 更贴合"这一下点击"的语义，不受其它手势干扰。

**仍未做（另案，不属 A-6）**：点选/旋转**共用一份**意图是"两个消费者各自判读同一批事件"；
若要真正**一次判读、多方消费**，需要像 A-6b 结论里说的那样在 `WorldRoot` 做"状态路由"——
那要等真有模态/建造模式时才做，现在不做。

## A-6b ｜输入分发的结论（**不建分发器**，供将来别再重推一遍）

**结论三句**：
1. **分发全用引擎的**：`_UnhandledInput` 通道（GUI 优先由引擎保证）＋ 信号 ＋ `SetInputAsHandled()` 表态
   ——不自建分发器、不套壳、不建 autoload（与"参数不建 Godot 单例"同一取舍）；
2. **判据自己写一次**：引擎只给原始事件，不给"这算点击还是拖拽"（= A-6）；
3. **状态路由（模态面板 / 建造模式）将来写在 `WorldRoot` 一处有序 `if`** ——那是中介者本职，不是新层。

**引擎已覆盖的分发需求**（别再造）：GUI 优先（`_GuiInput` ↔ `_UnhandledInput`）、
同一手势择一（树序 + `SetInputAsHandled`）、多播（信号）、
**键位映射与可重映射（`InputMap` + ui_* 动作 + `Input.IsActionPressed`）**、轴与组合（`GetVector`/`GetAxis`）、
屏蔽（`Control.MouseFilter` / `SetProcessUnhandledInput(false)`）。
**引擎唯一没有的是"按状态改路由"** ⇒ 一行 `if`。

⚠️ 代价与纪律：引擎的"优先级"= **场景树排列** + `SetInputAsHandled()` 表态
⇒ **挪一个节点可能静默改变优先级**（`OrbitalCamera` 顶上那条 `_Input` → `_UnhandledInput` 的 bug 记录就是现场）。
想让它可见就用注释钉住约定，或等 A-6 的判据工具。

在 `WorldRoot` 加一个显式方法（它是中介者，只有它同时看得见 `World` 与 `Render`）：
```csharp
public void RegenerateWorld()
{
    World.Regenerate();                 // ① 重算全部世界事实（Sim.Run）
    Render.RebakeView();                // ② 重烘表现（→ WorldView.Rebake）
    // ③ 模式表**不需要**重建 —— 见下方修正
}
```
★②不能少：`Sim.Run` 换掉的是各阶段**数组实例**，视图不重烘就会继续画旧场；
这条不变量已收口在 `WorldView.Rebake()`（A-1 第一轮的成果），接线只需一行调用。
★**③ 作废（2026-10-11 核实）**：原文写"若模式表持有旧引用需重建"——**不需要**。
依据在 `WorldGenMapModes.cs` 自己的头注释："模式持 `WorldGenSimulation` 引用（纯逻辑入口，
非 Godot 节点）、`CellColorAt` 时**现取**当前数据——`Run()` 会换数组实例，
持实例引用会读到旧场（读属性不存数组引用）"。即 `Sim` 实例**自始至终只有一个**，
`Run()` 只换它内部各阶段的数组 ⇒ 模式经属性现取，天然读到新数据。
（原文那条是"防御性怀疑"，实测设计已排除它。**别为它写代码**。）

**验收判据**：改 `Params.Active` 某字段 → 调 `RegenerateWorld()` → 画面与信息卡读数都变；
主场景 headless 零 ERROR；读数场景仍同基线（它自建 sim，不受影响）。

**触发时机**：参数面板 / 存读档恢复世界落地时（那是它真正的消费者）。

## A-6c ｜依赖为什么必须用 `NodePath`（**实测结论**，供将来别再试一遍）

**缘起**：审查管理器依赖注入时问"必须要用 NodePath 吗"——若能改用直接引用
（`[Export] WorldGenPlanet Planet`），则类型由引擎保证，四处 `Require<T>` 的"类型不符"分支可以删掉。

**实测（2026-10-11，一次性实验，已完整回退）**：把 `WorldManager.PlanetPath` 改成
`[Export] public WorldGenPlanet PlanetPath`，重建后跑主场景 ⇒ **启动即抛**：
```
ERROR: System.InvalidOperationException: [WORLDMANAGER] 依赖未配置：PlanetPath
   at World.WorldGen.WorldRoot._Ready() → WorldManager.Initialize
```
即 **`PlanetPath` 是 null**，引擎根本没把场景里那个节点绑上去。

**结论：本项目的依赖**必须**用 `NodePath`**，因为**依赖跨独立场景**。9 处 `[Export] NodePath`：

| 导出点 | 目标 | 目标来源 |
|---|---|---|
| `WorldRoot.PlanetPath`（经 `WorldManager`） | `WorldGenPlanet` | **另一个 packed scene** `scenes/worldgen/WorldGenPlanet.tscn` |
| `WorldRoot.CameraPath` | `OrbitalCamera` | **另一个 packed scene** `scenes/camera/OrbitalCamera.tscn` |
| `UIManager.DockPath` / `CellCardPath` | `MapDock` / `CellInfoCard` | **另外两个 packed scene** |
| `RenderManager.WorldViewPath` | `WorldView` | **另一个 packed scene** `scenes/render/WorldView.tscn` |
| `WorldRoot.{World,Render,UI}ManagerPath`、`UIManager.PanelLayerPath` | 同名节点 | 主场景内（这几个本可用直接引用，但**只有它们能**） |

★Godot 的"直接节点引用导出"只对**同一保存场景内**的节点可靠；指向被实例化的子场景节点时
不会跨场景边界绑定。本项目**所有**跨层依赖恰好都是"指向另一个 `.tscn` 的根"
（这正是"每个管理器持有一棵可替换子树"的代价）⇒ 只能走 `NodePath` + 解析 + 类型校验。

**因此那条 `Require<T>` 不是仪式**：`NodePath` 的静态类型是路径、不是节点，
"解析失败 / 类型不符"这两种运行时错误是 `NodePath` 方案的**固有代价**，必须有人照出来
（照出来 = 启动即失败，不留到运行中途）。⇒ **四份 `Require` 的合并仍然值得做**（见上一轮讨论：
收进装配层一个 `NodeDependency` 扩展方法），但**不能借"改用直接引用"来删掉它**。

⚠️ 顺带记录：实验期间场景文件里那行 `PlanetPath = NodePath("WorldGenPlanet")` 在类型改成节点后
仍会被 Godot 保留文本但不绑定（本项目的 `.tscn` 是**手写**的，不是编辑器存出来的）
⇒ 实验必须"改回类型 + 重建 + 跑场景"三步才算回退干净（本次已按此验证：`camDist=3.40` 逐字不变）。

## A-6d ｜`Require` 四份重复 → 收进工具层（**已落地**，2026-10-11）

**缘起**：审查管理器依赖注入时问"manager 里的 `Require` 是不是可以放 utils 里" →
"`Utils` 不该放 Godot 依赖" → 用户拍板**"util 也放开吧，可以放 godot 依赖的工具"**。

**实测规模**：四个管理器**各抄一份**同型代码（`WorldRoot` 的 `Require` + `Check`、
`WorldManager` / `RenderManager` / `UIManager` 各一个 `Require`，合计约 90 行），
且已出现**文案漂移**（`WorldRoot` 那份比其余三份多一句括号补充）。

**落地**：新增 `scripts/Utils/Scene/NodeDependency.cs`（`World.Utils`）——
`Require<T>` / `Check<T>` 两个**扩展方法**；四个管理器各删掉自己那份，调用点改 `this.Require<T>(...)`。

| 项 | 结果 |
|---|---|
| 异常前缀 | 自动取 `host.GetType().Name`（`WorldRoot` / `WorldManager` / …）⇒ 不再手写 `[XXXMANAGER]`，**结构上不可能漂移** |
| 调用点 | `this.Require<T>(path, nameof(path))`；`Check` 同型（顺带消掉 `WorldRoot` 里那个 `(NodePath, string, Type)[]` 元组循环） |
| 重复量 | 90 行 → 一份（约 60 行含文档） |

★**踩到的语法坑（值得记）**：扩展方法**不能裸写调用**——`Require<T>(a, b)` 报 CS0103
"名称不存在"（编译器只在**成员查找**里找扩展方法，不在普通静态调用里找）；
必须写 `this.Require<T>(a, b)`。五个调用点各改一处即通过。

**边界（放开 Utils 之后的唯一要紧约束）**：
- ✅ 允许：Godot **类型与结构**（`Node` / `NodePath` / `Vector3` / `Color`）；
- ❌ 禁止：**运行期引擎调用**（`GD.*` / `Engine.*`）——无引擎宿主的单测进程里是**进程级崩溃**。

**契约（本次新增，可执行）**：`ArchitectureContractTests.Utils_MayUseGodotTypes_ButNoEngineRuntimeCalls`
① 结果钉：`World.Utils*` 下不得引用 `Godot.GD`；
② 正向桩：同一扫描器必须在 `WorldRoot` 上看得见 `GD`（否则①是假绿）；
③ 正向钉：`NodeDependency` 必须存在且引用 `Godot.Node`（证明"语法面放开"真的落地）。
★**已做负向对照**（2026-10-11 实测）：临时往 `NodeDependency` 塞一行 `GD.Print` ⇒ 契约**当场报红**
并点名 `World.Utils.NodeDependency`，删掉后复绿 ⇒ 它不是空转。

⚠️ 扫描面局限（写在明处）：只覆盖**本程序集内联**的调用；外部预编译程序集内部的调用扫不到
（本项目无此结构，故不为此增加复杂度）。

**实测验收**：构建 0/0；单测 **313/313**（原 312 + 本条契约）；
主场景 headless exit 0 / 零 ERROR；读数逐字同基线。

**连带文档**：`重整方案-按架构分层.md` §二（`Utils` 条目补边界）、
`开发规范.md` 新增 §1.5（工具层的 Godot 边界）、`裁决-SceneLogic两分区.md`（标注两分区已被八层取代）。

## A-11 ｜"窄口接口"被用来绕过分层约束（用户 2026-10-11 判定：**不应该存在**）

| 接口 | 病的真相 | 正确修法（不引任何新类型） |

**"这个组件/数据本来该住哪一层？"** 若答案是"搬过去就自然不需要接口"，那接口就是取巧。
**不要用"接口够不够窄"当判据**（1 个方法的接口也能是取巧）。

**修法（待做，与地图坞重设计合并）**：
1. `MapDockController.cs`：`UI/` → `Scene/`（namespace `World.UI` → `World.Scene`）；
2. `IMapModeHost.cs` **删除**（驱动搬对层后无人需要它）；
3. `IPickedCellLabels.cs` **删除**；海拔分档表搬到世界侧（`Data/Constants` 或世界事实层），
   `ElevationMode`（色带）与 `UIManager`（文案）**各读同一张表**——单一事实源不靠接口转发维持；
4. `UIManager` 去掉 `modes` 参数与 `using World.Render`；`WorldRoot` 改为自己建驱动器。

## A-12 ｜R2"引擎侧三层平级"没有可执行契约

**症状**：`重整方案` §四把 R2（`Render`/`UI`/`Client` 平级互不引用）写成规则，
但**没有任何测试盯着它**——`ArchitectureContractTests` 里没有一条检查"某层的 `using` 白名单"。
后果（本次实证）：我在 `UI` 里加 `IMapModeHost` 时，**契约一声没响**；
依赖边是靠人工逐层列 `using` 才发现的（见 A-10 的审计手法）。

**为什么这是根因之一**：约束不可执行 ⇒ 每遇到跨层需求就得**临场发明机制**（窄口、包装、转发），
而每次发明都能自我说服。**把约束写成机器可验，就不需要临场发明了。**

**修法**：仿既有形态（`Utils_MayUseGodotTypes_ButNoEngineRuntimeCalls`、磁盘白名单、
`WorldParams_AreReadOnlyByTheLogicLayerGate`）加一条**逐层 `using` 白名单契约**：

| 层 | 允许引用 |
|---|---|
| `World.Data` | `World.Constants` |
| `World.Utils*` / `World.H3Grid` | `World.Utils*`（+ 类型面可用 Godot） |
| `World.Logic` | `World.Constants` / `World.Data` / `World.H3Grid` / `World.Utils*` |
| `World.Render` | 上述全部（表现层消费世界事实） |
| **`World.UI`** | **`World.Data` / `World.Constants`**（★哑组件层**不得**引用 Render） |
| `World.Client` | `World.Constants` / `World.Utils*` |
| `World.Scene` | 全部（装配层本该如此） |

★须带**正/负向自检**：正向 = 各层至少被扫到 N 个类型（防"扫描器瞎了"）；
负向 = 临时插一条越界 `using` 必须报红（本仓库已有此先例：`Utils` 边界契约做过负向对照）。

**触发时机**：与 A-11 同批（先删接口，再加契约——否则契约会先把现状判红）。

## 附：2026-10-11 编码事故记录（防复发）
本轮用 PowerShell 的 `Set-Content` / 字符串管道批量改注释，造成：
`W`→`o`（5 个文件：`namespace World` → `oorld`）、`oavelength` 系列属性名残缺、
`WorldGenPlanet.cs` / `WorldRoot.cs` / `UIManager.cs` 整文件不可读。

**根因**：PowerShell 默认按系统 ANSI（GBK）读写，与仓库的 UTF-8 无 BOM 不一致，
且管道会静默转码。

**纪律（已生效）**：改源代码只用**编辑工具**或 `[System.IO.File]::WriteAllText(..., UTF8(no BOM))`；
**禁止**用 PowerShell 字符串管道改写 `.cs`。若必须脚本化 ⇒ 先 `ReadAllBytes` 校验 UTF-8 合法性再写回。
